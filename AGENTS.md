# Working in this repo

A Godot **4.7** co-op game template: a procedural planet with a sea, under a vivid shader family, pencil-drawn menus, LAN lobbies, an animated first/third person character that walks, flies and swims, a wardrobe with apparel, two weapons, and text plus push-to-talk voice chat. Everything is built to be **taken over and turned into a different game** by editing data tables and assets rather than rewriting systems.

`README.md` is the prose: why each system is shaped the way it is. **This file is the map**: where each concern lives, what to edit to change it, how to verify the change, and which mistakes cost the most time. Read the matching README section before redesigning anything — most surprising decisions are deliberate and explained there.

## How to work here

- **Every concern has one file that owns it.** Change the game by editing that file, not by adding a parallel system beside it. The tables below name the owner for each concern.
- **New files follow the existing homes**: `core/` session-wide services (autoloads), `game/` gameplay scenes and scripts, `ui/` menus, HUD and themes, `shaders/`, `blender_assets/source/` asset authoring scripts, `dev/` throwaway and harness scripts. Nothing outside `dev/` should reference anything inside it.
- **Keep testing very light.** The owner's standing preference, for every agent and every request: **the bar is that the game still runs.** One short run that boots the thing you changed and exits clean, with no errors in the log. Not a sweep, not a battery across every harness, not a characterisation of the new behaviour — the owner does the real testing and will ask for numbers when numbers are wanted. Prefer extending an existing harness to writing a new scene, and prefer no new scene at all. Every feature here has a harness (see below) if you do need one; they print numbers and write screenshots to `dev/captures/` (gitignored).
- **Delete your scaffolding.** Temporary probe scripts go in `dev/` and get deleted in the same session.
- **Comment the constraint, not the code.** The house style states what the code cannot: a unit, an ordering requirement, a rejected alternative. Never narrate what the next line does, and never write comments addressed to a reviewer.
- **GDScript is statically typed** throughout (`:=`, typed loop variables, typed signal parameters). Autoloads are reached by their global name (`NetworkManager`, `ChatManager`), never by `get_node("/root/...")` except where an autoload may legitimately be absent.

## Run and verify

On this machine:

```powershell

cd c:\Users\ellio\Desktop\Planet
```

These three lines have each been wrong at least once and cost a run to find out. **Check them before quoting them**: the Godot download unpacks into a directory named after the archive, so the binary is two `Godot_...` deep and not one; Blender is installed per minor version and updating it leaves the old directory behind, so `Get-ChildItem "C:\Program Files\Blender Foundation"` is the honest answer to which one exists.

**The project does not run without the native terrain.** `bin/libplanet.*.dll` is committed, so a clone works; a change to `native/src/` does not until it is rebuilt. Godot holds the library open while it is running, and the link then fails with `Access is denied` rather than anything about the file being in use — close every Godot instance before building.

**Anything that puts the player somewhere must do it in the landing site's frame, not in world coordinates.** The world origin is the planet's *centre* now, so `Vector3(11, 0.4, 11)` is 8 km underground rather than a spot on the grass, and a world yaw does not face anything in particular. `_weapon_test` shows the shape of the fix: it reads the `LandingSite` anchor's transform once and `_place()` measures every offset and turn in that, which left all four of its call sites saying what they always said. Rebuilding the flat arena as a dev-only scene was considered and rejected — movement on a sphere is what actually needs testing, and a flat bench would pass while the real thing failed.

**`_player_test` is the one still short**, and it needs rethinking wholesale rather than patching: it lays a 1.6 km speed runway along flat ground at `y = 0` and drives kerbs and props that no longer exist. `_weapon_test` passes except for `clip=Fall` where a run clip belongs, and that one is a placement nuance, not a gravity one — its offsets are measured on the site's tangent plane, and 15 m out the real ground can be a metre below it, so the player is dropped rather than stood up. Taking the height from `Planet.standing_position` instead was tried and made the firing line flakier, so it was put back. Everything else passes.

Three gotchas about verification itself:

- A script with a new `class_name` is invisible to other scripts until the project is reimported. `Could not find type "Foo"` almost always means the import above has not been run.
- `--check-only --script some_script.gd` reports bogus `Identifier not found: NetworkManager` errors, because that mode runs without autoloads. Use a harness scene instead.
- Harnesses that touch audio or take screenshots must run **windowed**. Headless has no audio device and no rendering.

## 1. Style: shaders, textures, palette, legibility, fonts

Everything in 3D is drawn by one shader family in `shaders/vivid/`; the menus are still drawn by the 2D half of `shaders/pencil/`. Read `shaders/vivid/README.md` before tuning — it is the authority on what each uniform does.

### The 3D look

Real lighting, exaggerated colour. **Godot's own PBR does the shading in every one of these shaders** — there is no custom `light()` function anywhere — and the style comes entirely from what is fed into it. Push the hues, leave the light alone, and the result reads as a bright real place rather than as a filter over one. Undo that split and the look collapses into a cartoon.

Six shaders and a library:

| Shader | Draws |
| --- | --- |
| `vivid_terrain.gdshader` | The planet's ground: biome from vertex colour, cliffs by slope, and the wet shading of the sea bed |
| `vivid_surface.gdshader` | Props, characters, garments, weapons, whatever a `.glb` arrives carrying |
| `vivid_space.gdshader` | Sky and open space, as one crossfade driven by the camera's altitude |
| `vivid_atmosphere.gdshader` | The lit band of air, on a shell `Planet` raises above the surface |
| `vivid_water.gdshader` | The sea, bent onto the sea-level sphere from a disc that follows the viewer |
| `vivid_clouds.gdshader` | The iridescent cloud deck, marched through a slab of air a kilometre up |

**The planet frame is seven global shader parameters**, declared in `project.godot` under `[shader_globals]` and read through `vivid_lib.gdshaderinc`: `planet_center`, `planet_radius`, `sun_direction`, and the `region_*` group that aims the colour wheel. Only `Planet._publish_frame()` writes them, and only the first three — the region controls are authored in `project.godot` and left alone at runtime. That is what lets a prop standing on the ground pick up the same region colour as the ground under it with no wiring between them.

The colour wheel is the answer to "different regions should reflect light differently". Hue runs around `region_axis` the way longitude does, so neighbours meet in a gradient and never at a border. Two rules keep that true: **`region_turns` must be a whole number**, because the hue is `fract()` of an angle and a fractional count meets itself on the far side as a hard seam; and the wander is added to the **angle**, not to the finished hue, for the same reason. `vivid_region()` is the one place this is decided.

Every shader takes the region in three doses that fail differently — `region_albedo` mixes it into the surface's own colour, `region_sheen` glows in `EMISSION` at grazing angles, `region_rim` is Godot's `RIM`. The albedo dose is the honest one and carries the effect; the other two are highlights and want to stay small, especially on terrain, where a landscape running to the horizon is nearly all grazing angle and a generous sheen is a wash over the whole frame.

**Flat art is made interesting by three things stacked on whatever albedo arrives**, which is what `vivid_surface.gdshader` exists for: the texture's own luminance read as height and used to bend the normal (the biggest win, and nearly free); two scales of 3D noise for grain and for blotchy macro variation; and roughness that varies with the same field so highlights break up. All of it is in **cycles per metre**, so numbers never carry between a 1.45 m character and a hillside — compare `player_suit.tres` (`detail_scale` 14) against `planet_surface.tres` (0.35).

**Detail must fade with distance.** Procedural noise has no mip chain, so a bump smaller than a pixel aliases into shimmer. Every detail field is gated by `detail_near` / `detail_far`, and the terrain's macro field needs a second gate of its own (`macro_near` / `macro_far`) because from orbit its 70 m blotches fall under a pixel and boil into speckle.

The environment is part of the look, not incidental to it. The sky is the ambient **and** reflection source, which is most of a stop brighter than a lone directional light — hence terrain `brightness` at 0.6 and the sun at 1.05. ACES tonemapping with `tonemap_white` 2.0 gives the sun's disc and the water's highlight somewhere to go. Glow sits at `glow_hdr_threshold` 0.95 because **the mobile renderer's colour buffer tops out near 2.0**, so a threshold at 1.0 means nothing ever blooms. `game/world.tscn` and `dev/_planet_test.gd` both set these; keep them in step.

Imported `.glb` meshes get the look at runtime from `game/player/surface_skin.gd`, which duplicates `game/player/player_suit.tres` per surface and copies **only** `albedo_color` and `albedo_texture` across. So recolouring or re-texturing in Blender carries through with no script change, but roughness and normal maps do not exist as far as this project is concerned — which is exactly why the shader manufactures its own relief. Character detail is tuned in `player_suit.tres`, not per mesh.

### Textures

`images/` holds 11 hand-made ~500 px textures, imported lossless with no mipmaps. **None of them are referenced from a Godot scene any more** — the props that used five of them went with the flat arena, and the planet's ground is procedural. They are still useful: assign one as albedo on a Blender material and `SurfaceSkin` picks it up, and `vivid_surface.gdshader` will read its brightness as relief. `vivid_terrain.gdshader` can take one too, through `ground_texture` and `ground_texture_blend`, triplanar and off by default.

### Colour and legibility

Five source colours in `ui/themes/ui_palette.gd` run the whole UI: Midnight Violet `#2d1e2f` for every panel, Vanilla Custard `#fcf6b1` for type on those panels and for **whatever holds focus and nothing else**, Sunflower Gold `#f7b32b` for a screen's primary action and its headings, Celadon `#a9e5bb` for every other button, and Burnt Tangerine `#e3170a` for leaving and failing only. Card and text tones are mixes of the first two.

The scheme is dark-surface, and one rule holds it together: **`PencilSurface` styles come in two families, and a control is never the colour of the thing it sits on.** `PAPER`, `CARD`, `ROW`, `INPUT` and `HUD` are containers — violet, holding custard type. `BUTTON`, `PRIMARY` and `DANGER` are controls — filled with one of the bright colours, holding violet type. Buttons used to differ from the card only by hatching density, which on one sheet of paper meant white on white; now they carry a fill of their own, and hatching is left to say what *state* they are in. Tangerine is the one fill dark enough to want custard type instead of violet, which `MenuWidgets.dress()` applies so no caller has to remember it.

Two more rules are easy to break by accident:

- **Colour carries meaning; state carries hatching.** Hover and press shade a fill in further (`fill_tone` drops), they never change hue, and a button's label keeps its colour in every state. Focus is the one exception: a thickened Vanilla Custard ring, drawn by `PencilSurface._set_focused()`. Custard is used at fill weight nowhere else, which is what keeps focus visible on a screen where every control already carries a colour.
- **Text over the 3D world never relies on its own colour.** The world behind a prompt can be pale sky or dark grass, so light-text-with-shadow and dark-text both lose. Every HUD line sits on an opaque `Style.HUD` plate sized to its text. The arrangement is `wrapper → PanelContainer (PencilSurface here) → MarginContainer → Label`, and because `PencilSurface.BLEED` (6 px) of each margin is spent on the gap between the panel edge and the drawn plate, **margins are written 6 px larger than the padding they should look like** (20/15 reads as 14/9). `game/player/player.tscn` and `ui/chat/chat_hud.gd` are the two worked examples.

Applying a surface is one call: `PencilSurface.add_to(control, PencilSurface.Style.BUTTON)`, or `PencilSurface.rule()` for a separator. `main_theme.tres` leaves the button, input and panel styleboxes **empty on purpose** so the shader reaches the control's edge; panel padding therefore belongs to an inner `MarginContainer`, never to a stylebox.

Two colour gotchas: `ui_palette.tres` carries **no** property overrides, so the real values are the script defaults; and `main_theme.tres` repeats several palette colours as raw floats because a theme resource cannot read a script export. **Recolouring the UI means editing both.** The theme is where the tab, popup, slider and scrollbar fills live, since those are stock `StyleBoxFlat`s rather than drawn surfaces.

Menus are sized off the window, not in fixed pixels: `MenuWidgets.panel_width()` takes a share of it with a cap, and `MenuWidgets.card(parent, padding, fill := true)` makes a card as tall as the band it is given rather than as tall as its contents. A filling card holds a `MenuWidgets.scroll_area()` or a `TabContainer` that takes up the slack, so **a form can never overrun the window however large the type gets** — which is the failure the old centred, content-sized cards had, where the overflow was split between the top and bottom edges and the submit button was the half that went missing.

### Font

`fonts/Barrio-Regular.ttf` is an outline stencil display face, imported with antialiasing, hinting and subpixel positioning all **on**. It is set both as the theme's `default_font` and as `[gui] theme/custom_font`, so controls that never reach the theme match anyway; **changing the typeface means editing both.**

There is no size grid — any integer is fine. The ladder in use is 14–17 for captions and the dense in-game panels (chat, weapon bar, tooltips, HUD lines, the menu's stat and quest rows), 19–24 for menu tabs, body and the name field, 26 for body and 28 for buttons, and 30/32/40/44/48/64 for headings, the settings title and the game title.

Barrio has no glyph for a pencil, a gear or any other icon, and a missing glyph in it comes out as a **stray sliver** rather than as a visible box — which is how the home screen's edit pencil started life. Icons are drawn (`HomeScreen._pencil_button()` is the pattern: polygons over a rim, redrawn on hover and focus) rather than set as text.

Barrio has **no bold weight**, so weight comes from an outline in the text's own colour: `outline_size` 3–6 with `font_outline_color` matching `font_color` thickens the stems without changing the letterform. The theme does this for `Button`, `OptionButton` and `TabContainer`; `MenuWidgets.heading()` does it for headings, in violet under gold. Type over the starfield is the exception — there the outline is near-black (`HomeScreen.SKY_OUTLINE`) because the planet's lit limb passes under it.

Sizes carried over from the old pixel font need scaling by about 1.45, because **Barrio's caps measure roughly 0.69× that face's at the same nominal size**; below about 12 the stencil breaks swallow the letterforms entirely. Barrio is also about 0.8× the width at matched cap height, so text set this way takes *less* horizontal room than the old face, not more.

**The tuning bed is `dev/_planet_test.tscn -- --tour`**: ten shots from 32 km down to standing on the ground, written to `dev/captures/` with chunk, triangle, draw and LOD numbers beside each. It is the only honest way to judge a change to the vivid family, because most of these decisions go wrong at exactly one range — speckle shows from orbit, tiling shows at a grazing angle along the ground, and the atmosphere rim exists only between the two. `dev/shader_lab.tscn` still drives the **pencil** shader and its command-line uniform overrides (`-- --set=parallax_strength:0.2 --freeze --shot`).

## 2. Features: movement, wardrobe, apparel, weapons, world

### The character controller

`game/player/player.gd` (`class_name OnlinePlayer`) is one file holding movement, camera, animation selection, HUD, interaction, equipment and weapons, with the network seams at the bottom. Tuning is exported, so most feel changes need no code: `walk_speed` 4.6, `sprint_speed` 7.6, `crouch_speed` 2.3, `jump_velocity` 12.0, `jump_speed_gain` 0.8, `coyote_time` and `jump_buffer` 0.12 each, `ground_accel` 60, `ground_friction` 48, `air_accel` 14 (deliberately weak), `run_spool_time` 30 (the seconds a held shift takes to reach `run_top_speed`, and the one number that decides how fast a run gets away from you — at 30 the target climbs about 6.6 m/s², a shade under the planet's own pull), `run_snap` 0.09 (metres of floor snapping bought per m/s of run: without it a run over rolling ground is a series of involuntary jumps, because a crest at 200 m/s falls away faster than the scene's 0.3 m over the 3.4 m the feet cross in one frame), `step_height` 0.3, `step_smooth_time` 0.08, and the slide group (`slide_speed` 10.5, `slide_entry_speed` 4.6, `slide_exit_speed` 3.6, `slide_friction` 5.2, `slide_max_time` 1.3, `slide_cooldown` 0.4, `slide_steer` 2.4). Metres, seconds, m/s, m/s².

**Gravity is the one movement number that is not an export here.** It is `physics/3d/default_gravity` in `project.godot`, set to **34 m/s²** — three and a half times Earth's, which is what stops a run at speed reading as a body that is barely in contact with the ground — and `_gravity()` is the single place that reads it. It belongs to the world rather than to the body falling through it; a second planet with its own pull is the day to move it onto `Planet`. Raising it shortens every jump, since apex is `jump_velocity² / 2g`: 12 m/s reaches 2.1 m here against 7.3 m at Earth's. It also decides how far a fall has to be before it becomes a crash — `CRASH_SPEED` 26 m/s is reached after 10 m of drop at this gravity, and after 35 m at Earth's. Gravity is only half of "the body feels heavy": `run_snap` is the other half, and a body that keeps leaving the ground on crests wants that one raised rather than this.

Three constant tables are indexed by enum and **their row order must match the enum**: `COLLIDER_HEIGHTS` and `EYE_HEIGHTS` by `Stance` (STAND, CROUCH, SLIDE, FLY, CRASH, SWIM — `[1.45, 1.2, 0.9, 1.45, 0.9, 1.45]` and `[1.29, 1.06, 0.78, 1.29, 0.6, 1.29]`), `ARM_LENGTHS` and `SHOULDER_OFFSETS` by `CameraMode` (FIRST, THIRD_NEAR, THIRD_FAR). New stances go on the **end**: the index is what goes on the wire.

Behaviour worth knowing before changing it:

- **Steps.** `_move_and_step` runs `move_and_slide` then `_climb_step`, which probes with `test_move`: back off the wall, lift above the obstacle, move forward, cast down for a landing. `_update_step_offset` and `_update_body_lean` then ease the visible body up so the climb is not a snap. Kerbs to ~0.36 m clear. The climb is gated on having footing, and that test is `is_on_floor` **or** `_footing_within(step_height)` — on the planet the first one says no far more often than the ground under the feet warrants, and a body airborne on a technicality treats every small bump as a wall.
- **Jump** buys forgiveness at both ends: coyote time after leaving the ground, buffering before landing.
- **Crouch and slide** resize the capsule from `COLLIDER_HEIGHTS`; standing up is gated on `CeilingCheck`. Worn garments never resize it.
- **Cameras**: `C` cycles, `Q` swaps shoulder. In first person the body is set to `SHADOWS_ONLY` rather than hidden, so it still casts a shadow, and a held weapon closer than 0.3 m to the camera is hidden the same way. The third-person arm is a `SpringArm3D` casting a 0.2 m sphere, which handles props and players; the planet it cannot handle, because the chunk behind the player may be drawn and not yet solid, so `_pull_camera_out_of_the_ground()` halves the arm against the same height field the body uses until the eye is `CAMERA_CLEARANCE` clear of the surface. It only ever **shortens** what the cast worked out, so it can never push the camera through something the cast did find.
- **Animation** is chosen in `_update_animation` by stance, airborne sign, and speed, with `Walk`/`Run`/`CrouchWalk` resampled by `speed_scale` so feet keep up. glTF carries no loop flag, so `LOOPING_CLIPS` sets it in code. Remote players infer "grounded" from vertical speed, since they are interpolated rather than simulated.
- **Interaction** casts `REACH` (2.4 m) **plus the spring arm length**, so third-person reach matches what the crosshair is on. Anything with `interact(player)` and `interact_prompt()` is usable.

### Flight

Space in mid-air takes off. Flight is `Stance.FLY`, not a flag beside the stances, which is what gets it synced, animated on remote players and validated by the host for free. It borrows the standing capsule, so take-off and landing never have to check headroom. There is no cancel key: a flight ends where it lands, and `_land_from_flight` trims the speed to `sprint_speed` on the way out. Tuning is the `Flight` export group; `-- --flight` on the player harness runs the whole arc and shoots each pose.

Four things bite if they are not known:

- **`_cruise` is a target, not an acceleration.** `boost_time` / `ease_time` / `brake_time` move it across the range and the velocity chases it at `flight_accel + _cruise * flight_turn`. Editing the accelerations to change how fast the boost winds up is the wrong dial; the times are.
- **The hover has two speeds.** `float_speed` 20 level or on the way down, `climb_speed` 11 straight up, mixed by how much of the wish points along `_up()`. Climbing is the one direction that is worked for; everything else reads as gliding and wants the pace to match. `float_speed` is also the take-off cap, the underwater cap and where `_fly_blend` starts, so it is the number to move if the hover as a whole is wrong.
- **Steering is the camera's basis, not the body's**, so pitch is what dives. Only the head pitches, so the camera's X stays level and a strafe never rolls the flight path.
- **The lean is the animation.** One smoothed `_fly_blend` drives `character.rotation.x`, the field of view and the choice between `Float` and `Fly`; the clips only cover the ends. It pitches about `LEAN_PIVOT` (the hips), because turning about the feet buries the shoulders. Both clips are authored **upright** in `build_animations.py` — in that file "up" is the direction of travel. Swimming does all of the same things through `_swim_blend` and `Tread`/`Swim`; see Swimming below.
- **Take-off and the jump buffer read the same press.** `TAKEOFF_CLEARANCE` (0.9 m of clear air below) is what keeps them apart; drop it and a press made just before landing takes off instead of buffering a jump, which the harness catches as `buffered jump  stance=fly`. It is also the floor under `jump_velocity`: a jump whose whole arc is shorter than 0.9 m can never become a flight, whenever the second press lands. At 5.6 m/s the apex was 0.46 m and it never could — the only routes into the air were a sprint jump and a ledge — which is why the standing jump is 12 and clears the line for over half a second.

On the wire, `_speed_limit(stance)` gives the host a per-stance ceiling and the teleport check is derived from it, so the ceiling for a client lying about its position is higher while it claims to be flying. Remote players are dead-reckoned on their last velocity for up to two packets (`_extrapolated`), because 50 ms at flight speed is ten metres.

### Swimming

`Stance.SWIM`, entered from `_submersion()` — how much of the body the sea has hold of, which is `PlanetWater.depth_at` over the capsule's height. **Chest deep is swimming; knee deep with something under the feet is not**, and the two thresholds (`SWIM_ENTER` 0.7, `SWIM_EXIT` 0.5) are apart because a swimmer floats at `1 / buoyancy` submerged and a single threshold anywhere near that would flicker between stroke and stride every frame.

`buoyancy` is a **multiple of gravity, not an acceleration in m/s²**, and that is the one thing to keep if this is retuned: the lift is `_gravity() * (buoyancy * fill - 1)`, so the body settles where the two terms cross — at 1.25 that is 80% under, floating with the head and shoulders out — and retuning the planet's pull does not quietly sink everyone. The harness measures the settled depth at exactly 80%. Everything scales with `fill` for the same reason: a stroke taken half out of the water pushes half as hard, which is what makes the surface somewhere the body settles rather than a line it has to be clamped to.

Five more things:

- **Held `sprint` boosts a swim the way it boosts a flight**, from `swim_speed` 3.4 to `swim_sprint_speed` 100 over `swim_boost_time` 6 s, coasting back over `swim_ease_time` 2 s, and only ever while a direction is being asked for. `_stroke` is the target the velocity chases, kept apart from the velocity for the same reason `_cruise` is; it is reset to `swim_speed` on **entering** the water, so surfacing and going straight back in does not hand the wind-up over for free. **`swim_surge` (4.0, extra acceleration per m/s asked for) has to stay above `water_drag` (2.6) or the boost is unreachable** — drag takes `water_drag * v` a second, so holding 100 m/s costs 260 m/s² against the 16 an unhurried stroke uses. Writing it per m/s rather than flat is also what makes the top speed the same with the shoulders out as it is ten metres down: the stroke and the drag are then both linear in `fill` and it cancels. `_water_test`'s **sprint** step reports the speed held and the lowest it sagged to over a second, which is the check that catches a surge set too low; 98 of 100 is what a correct one reads.
- **A boosted swim is spent on wading ashore and kept on breaking the surface.** Both leave `Stance.SWIM` through the same branch, and the `grounded` test is what tells them apart: with something under the feet the velocity is clamped to `sprint_speed`, because the ground has no way to have earned a hundred metres a second. Without it the body is thrown clear, which is the whole point of swimming up hard.
- **Water drag applies to flight too.** The sea has no collider so a flight goes straight through it, but `_fly_move` caps `_cruise` at `float_speed` and sheds speed at `water_drag` while submerged — otherwise a 200 m/s dive carries on to the sea bed and crashes into it. A 40 m drop now stops 15 m under.
- **Two presses of `jump` take off out of the water**, inside `SWIM_LAUNCH_WINDOW` (0.4 s). Jump is also the up-stroke, so the first press has to stay a stroke toward the surface or a swimmer cannot surface at all; the second is the launch. `sprint` + `jump` was the older rule and did the same job, but a key combination in a game with no combinations anywhere else is one nobody finds. Neither press needs `TAKEOFF_CLEARANCE`: that exists to keep a take-off apart from a buffered jump, and a swimmer has no jump to buffer, so asking for it would refuse a launch out of anything shallower than a metre.
- **Swimming has the same two clips and the same lean as flight**, an order of magnitude slower: `_swim_blend` runs 0 treading to 1 laid out, picks between `Tread` and `Swim`, and pitches the body about the hips through the same expression `_fly_blend` uses. It is a separate number rather than a reuse of `_fly_blend` because that one also opens the field of view, and a 3.4 m/s breaststroke has no business doing that. The two blends are combined with `maxf`, not a sum, so a launch out of the water carries the lean across instead of standing the body up for the frames both are moving. The swim's share of the **field of view** is a third number, `_swim_rush`, read off how far `_stroke` has wound up rather than off the speed reached — the lean is finished by the second stroke and the rush has barely started, and reading the velocity instead would have the view breathe through every turn taken at speed.
- **Splashes are local to everyone.** `_track_water_crossing()` runs for remote players as well, off their synced position and velocity, so nothing is spent on the wire saying someone went in.

### Items and containers

`game/items/item_db.gd` is the whole catalogue — eleven items today: five garments cut for the astronaut (`straw_hat`, `flight_goggles`, `rust_long_sleeve`, `denim_trousers`, `leather_shoes`), four for the settler (`c3_hair`, `c3_goggles`, `c3_tunic`, `c3_boots`), and two weapons (`sword` blade/swing, `laser_rifle` rifle/shoot with a 12-shot cell). Each entry carries `title`, `description`, `slot`, `scene`, and a `tint` used as the icon fallback; weapons add `hold`, `attack` and `cell`. `SLOT_ORDER` is also the UI order of equipment slots, and it runs head to feet: `hat`, `goggles`, `long_sleeve`, `pants`, `shoes`. **Inserting a slot in the middle is safe** — every index into the equipment container is derived from that constant at run time, and a saved look keys its garments by slot name rather than by position.

`game/items/item_container.gd` is a fixed run of slots with per-slot filters, and it is what makes equipping ordinary: the player's `equipment`, `weapons` (5) and `backpack` (36), and a station's `storage`, are all the same class. `transfer` is a **swap** that validates in both directions, so a permissive source slot cannot smuggle a hat onto the feet; `quick_move` is the shift-click path. The player watches `equipment.changed` and turns it into garments on the skeleton, which is why the menu preview cannot drift from the body in the world.

### The menu, the inventory and apparel

`ui/menu/game_menu.gd` is the one card, with Hero Design, Inventory, Quests, Achievements, Settings and Admin across the top. It replaced two screens — the wardrobe card and the pause overlay — and that is the point of it: both were opened by a key, both took the mouse, both dimmed the world, and having two meant `Escape` and `Tab` led to different places under different rules. Now **`Tab` opens it on Inventory, `Escape` on Settings, and either key shuts it from any tab**. The menu does not decide what pausing means; it says it is open and `GameWorld.set_local_pause()` decides.

Both keys are handled in `_input` rather than `_unhandled_input`, because `Tab` is also `ui_focus_next` and the GUI would otherwise spend it walking between tiles, and `Escape` would reach the world first. The one exception is written into `GameMenu._input`: **while a chat line is open, `Escape` belongs to the field**, or abandoning a message shuts the menu out from under it.

`ui/inventory/inventory_page.gd` is Hero Design **and** Inventory, in game and again in the home screen's character editor — one class, four places, and that is deliberate rather than convenient. Dressing a character is dressing a character; a second screen for doing it before the game starts would be a second place for the tiles, the filters and the quick-move rules to drift. Two switches cover the differences:

- **`section`** picks which half is built. `HERO` is the figure, what it is wearing, its stats, its weapon bar and the colour wheel; `POCKETS` is the grid and the filters over it. **Both callers build both halves and put a tab over them**, against **one set of containers**, so an item moving on either tab redraws the tiles on the other with no wiring — two instances rather than two classes is what buys that.
- **`show_preview`** is off wherever the caller already has a model of this character on screen, and the page then costs no `SubViewport` at all.
- **`catalogue`** says the pockets are a list of everything this character owns rather than a bag of what it happens to be carrying. See below; it is the character editor and nothing else.

`editing` is the fourth and it is much smaller than it was: the name is typeable and the pockets are stocked from the body's wardrobe rather than from a backpack. It no longer changes the *shape* of either half, which is the point — the editor and the in-game screen now hold still against each other.

**The tab strip is `MenuWidgets.fill_tab_row`**, one function filling whatever `HBoxContainer` it is handed. Both screens carry the same two tabs and a second copy of the strip is a second place for the open tab to be marked differently. It rebuilds from one integer rather than restyling in place, because a strip redrawn from the current index cannot end up with two tabs both looking open.

The page owns **no item state** — every tile points at a slot of an `ItemContainer`, and equipping is an ordinary move. Item icons are rendered from each item's own mesh by `ui/inventory/item_icons.gd`, so there is no second copy of the art to keep in step, and both the icons and the live preview render **supersampled** (`PREVIEW_SUPERSAMPLE`) because outline width is measured in pixels and a 44 px icon would otherwise be ringed in strokes as thick as the garment.

The in-game pockets grid is **wide and shallow on purpose**: `COLUMNS` times its rows has to come to the backpack's size or the last row comes out ragged. `GameMenu` gives the card the window's height less `TAB_ROW_ROOM` and the same height on every tab, so the strip across the top does not jump when a tab is pressed. That leaves most of the card blank on the Inventory tab, and blank is what it now is — there was a captioned "Reserved" well there and it is gone. A well is a control, and a control the size of half the card reads as the screen's main feature however it is captioned.

**A catalogue is not a bag, and the difference is where an item lives.** In game the grid is a backpack: a hat is *in* there, so wearing it takes it out and the tile empties. In the character editor there is nothing to carry and no wardrobe to walk to — the grid is a list of every garment cut for this body, from `CharacterDB.apparel_ids`, and wearing one changes only how its tile is drawn. That is what makes "the equipped item still shows, with a box round it" possible at all; a container the item had been moved out of has nothing left to ring. Three things fall out of it and each is load-bearing:

- **The rail is sized to the wardrobe, not to a grid.** `HomeScreen` builds `_apparel_rail` with one slot per garment and `_stock_editor` fills every one of them, worn or not. There is no free slot, because nothing ever arrives.
- **Clicking equips, and clicking again undresses.** `_wear` writes the equipment container directly rather than moving anything, and toggling is not a nicety: the tab has no other way to take a hat off, and a click that only ever equips does nothing at all half the times it is used.
- **Catalogue tiles do not drag** (`ItemSlot.draggable`). A drag is a `transfer`, which is a swap, so dropping a worn garment onto a catalogue tile would put it in a list that is supposed to hold everything and displace whatever was there. Clicking and hovering are untouched, which is all a catalogue needs.

**The two filter rows are toggles, not a radio group**, and pressing the open one clears it. That is what saves an "All" button on each row, and it is the same idiom the worn tiles use to hand the colour wheel back to the skin. A category is derived from the item's slot rather than stored on it, so nothing has to be tagged: `ItemDB.WEAPON` is a weapon, any other slot is clothing, and something worn nowhere is an item — which is the row a future consumable lands in with no edit. The second row is the sub-divisions of whatever the first has chosen, so it is there under Clothing and absent under the other two rather than five greyed-out garment names over a grid of rifles. The catalogue is the one place with no "everything" state: it opens on Clothing, so both rows are up on arrival and there is no state in which the second one is missing until you go looking for a weapon.

Filtering **hides** the tiles that do not match, and a `GridContainer` lays out only its visible children, so the survivors close up instead of leaving the grid full of holes. Empty tiles go with the filter: a narrowed grid is a search result and a blank is not a result — and a catalogue, having nowhere to drop anything, never shows a blank at all. `_refresh_pockets` does the visibility and the worn ring in one pass, because both are answers about the same tile taken from the same containers and both have to be taken again whenever anything moves. `dev/_menu_test.tscn` prints `all=36, Clothing=1, Weapons=1, Items=0` and `dev/_menu_shot.tscn` prints `tiles=4 ringed=4` and `ringed=3` after one toggle — which is the whole behaviour, and the only way to see it, since a row of buttons that does nothing photographs exactly like a row that works.

**The colour wheel paints whichever worn tile is selected, and the skin when none is.** There used to be a row of buttons here naming every garment on the body — a second control saying the same thing as the equipment tiles a few centimetres above it, rebuilt from the container every time anything moved purely to stay in step with them. A tile is already on screen, already knows what is in it, and already draws a selected state for the weapon bar, so `ItemSlot.picked` is all it took; clicking the selected tile again lets go of it, because there has to be a way back to the skin that is not taking the hat off. `_set_tint_target` is also where a target that has just been taken off is dropped, or the wheel would silently paint a garment nobody can see, and it is where the wheel is moved to whatever that target has already been painted — otherwise every target opens on white and the marker says nothing about the colour under it.

`ui/inventory/colour_wheel.gd` is the control: a hue-and-saturation disc, a value bar, and the chosen colour along the bottom. It replaced ten fixed swatches, which could only ever offer ten answers to a question with no natural shortlist — a tint multiplies an authored-white body, so the whole space is reachable. **The commit is on release and not during the drag**, and that is a cost decision rather than a matter of feel: both owners of `picked` write the look to `user://settings.cfg` and the in-game one reads it back first, so a signal per frame of a drag would be a file round trip per frame. The swatch along the bottom is what the drag feeds instead, so you see the colour you are about to commit without anything outside the control being told.

A tint multiplies the albedo it finds, so every pick is laid over a freshly painted model rather than over the last one, and materials are derived per target so a material the body and a garment happen to share cannot carry one's tint onto the other. **It multiplying is also why every asset ships white** — see §3; over the old baked-in colours nine of the ten swatches came out as the same near-black.

**Height is the axis this page runs out of**, and the wheel is the tallest thing on it, which is why the disc is 118 px and not the 132 it was drawn at. The editor's card is the binding case: it is a share of the window with the figure standing in the rest, and it lost 54 px to the tab strip it just grew. `dev/_menu_shot.tscn` prints `card wants WxH` against the room the anchors allow and fails the run if it is over, which is the only way to see this — a card bigger than its host drags the host past its own anchors instead of being clipped by it, so every frame still looks plausible and the window quietly loses the bottom row. The colour block is also **wider than the wheel** (`TINT_BLOCK_WIDTH`), because the line naming what is being painted wraps to three lines at the disc's own width and width is the thing this card has going spare.

`game/player/wardrobe.gd` does the attaching: pull the `MeshInstance3D` out of the garment `.glb`, parent it to the body's `Skeleton3D`, point its `skeleton` at that parent. Garments are skinned to the body's own 23 joints, so they animate with no extra work.

**A shell garment cannot clip at rest, so a rest-pose render proves nothing about fit.** Every garment here is a region of the body pushed out along the body's own normals with the body's own skin weights, so at rest the two surfaces are parallel by construction — and the build says so, reporting zero for all five. What they cross under is a *pose*: a shell and the skin beneath it sit a couple of centimetres apart, and linear blend skinning does not preserve that gap, because on the inside of a fold the outer surface has further to travel and arrives short. So `build_apparel.py` prints two numbers per garment, the rest-pose one and the worst over a few frames of `Walk`, `Run`, `CrouchIdle` and `JumpRise`, with the body coordinate of the worst vertex beside it. The offsets in the file are sized against that second number and nothing else: the shirt went from 14 mm to 22 mm, the trousers from 17 to 23 and the shoes from 20 to 24, all of it bought back at a knee, a toe box and a shoulder that had been crossing by up to 29 mm.

Two measurement traps sit in front of that report, and both return numbers so wrong they look like a broken garment rather than a broken ruler. **The depsgraph hands back the body in whatever pose the `.blend` was saved holding**, which after a bake is the last frame of the last clip — measured through that, an untouched sleeve reported 373 mm of bare skin, all of it an arm that had swung out from under it. And **the body's Decimate makes a per-vertex mask impossible**: it is a collapse, so feeding it a posed body changes which edges it chooses and the mesh that comes out has a different topology per frame, which had index 400 as a shoulder at rest and a shin two frames later. The fix for the first is `pose_position`, not switching the Armature modifier off, because that trips the second; the fix for the second is to drop the Decimate for the posed pass, which costs nothing, since what the collapse is worth is measured separately against the rest pose and comes to 2.1 mm.

**A hem is cut by a plane, and a plane laid across a surface that is nearly parallel to it does not cut a circle.** It wanders over the quad grid a face at a time and comes out as a sawtooth, and no amount of bisecting first prevents it — the cut is genuinely ill-defined there. The astronaut's collar sat 50 mm above the neck landmark, which is exactly the shelf where the shoulders run into the throat and the most up-facing band on the body, and the neckline was visibly torn in every pose for as long as it was there. It is now seven tenths of the way from the neck to the skull, where the neck is a wall, and the same cut is clean. Anything new that opens against a shoulder, a hip or the top of a foot wants checking for this before its thickness is touched — measure the band's mean face normal and put the hem where the surface is steep.

`HEM_BURY` is the other one that has to clear a measured number rather than look plausible. The flange folded back through each opening ends that far past the *base* skin, and the body ships decimated and stands a little outside the base mesh; at the 2 mm it was against a 2.1 mm bulge the fold closed exactly on the line and roughly half the rim lost, so every opening in the wardrobe wore a comb of bare skin one mesh edge deep. It is 10 mm now, and deeper costs nothing because the flange is inside the body either way.

**A garment that both bodies want is written once, as a function of the landmarks.** `build_apparel.goggles_spec()` is the worked example: `build_character_3.py` calls it with its own slug and colour, and the result is a pair that fits either head with nothing measured twice. That is only possible because every number in it is a fraction of the head's own size rather than of the figure — the two characters differ by 15 cm of body and 7 mm of skull, so a spec written against height comes out a size wrong on one of them. `Landmarks.head_width` exists for the same reason: their heads are five centimetres apart in width and one in height, so anything worn on the face is spaced against the width.

### Picking and dressing a character

**The home screen's pencil opens the same two tabs again**, in `editing` mode, and the reasoning is the one above carried one step further: dressing a character before the game starts and dressing one during it are the same job. Editing mode makes the name typeable, points the pockets grid at the garments cut for the chosen body, and drops the dimmer and the centring — a dimmer would only cover the band the home screen hands the screen and show its own edges, and a centred card lands on the very figure being edited, so the card is held against the right the way every other home-screen form is.

**It shows base stats and an empty weapon bar rather than wells explaining their absence.** `PlayerStats` needs nobody to exist, so the editor can print the numbers a new character starts with, which is worth seeing while choosing the body they hang on; and five tiles nothing can be put in are worth the room because the alternative is a bar that *appears* between the editor and the first time the menu is opened, moving everything under it when it does. Both are `HomeScreen`'s to supply — `_editor_weapons` and `_editor_stats` are held on the home screen rather than in the page, because the editor is thrown away and rebuilt every time it is opened.

**And it has no preview of its own**, because there is already one: the figure hanging at the spawn behind the card *is* the character being edited, lit by the world's own sun and wearing exactly what the containers hold. The page used to render a second one into a `SubViewport` a couple of hundred pixels wide, so the screen carried two models of the same character disagreeing about the light and about which way round they were turned. `show_preview = false` and `EDITOR_CARD_SHARE` are the whole of it — the card takes the right of the window, the figure keeps the left, and dragging anywhere outside the card spins it, which is why `HomeScreen._unhandled_input` allows the CHARACTER view as well as HOME. Being over on the right is also what lets the editor's card start at `EDITOR_TOP` rather than under the full title band: the title is 56 px from the left edge, so a card that begins past the middle is not underneath it. That was 84 and is now 52, because the tab strip costs 54 px the card had to find somewhere; the card clears the title horizontally now rather than vertically, which is enough.

**The screen reports a pick rather than acting on it.** `body_picked` and `tint_picked` go to whoever opened it, because the body and the colours are exactly the state the screen deliberately does not keep: they have to outlive it and be handed to the spawn. `HomeScreen` owns the two containers, writes every change through `CharacterDB.save_look()`, and hands the result to `GameWorld.override_local_look()` when New Game is pressed. Garments are the exception that needs no wiring — they live in the equipment container, which is the same container the in-game screen moves items in, so the look is read back out of it.

`game/player/character_db.gd` is the catalogue: per body, the `.glb`, the collider and eye heights and lean pivot that go with it, and **which garments were cut for its skeleton**. The two bodies share slot names so the equipment column keeps its shape, but a garment only binds cleanly to the skeleton it was authored against, so `apparel_fits()` gates it in three places — the rail is stocked from it, `worn_items()` filters the wire, and `OnlinePlayer._dress()` refuses a mismatch outright.

Two things about tinting bite:

- **A tint multiplies the albedo it lands on**, so it cannot be applied over itself: three picks in a row would give the product of all three. Every path that tints therefore repaints from the mesh's authored colours first — `SurfaceSkin.paint`, then one `tint_material` per derived material. Materials are derived per target rather than across the model, so tinting a garment cannot reach the body through a material the two happened to share, and one material shared by two meshes is still tinted once.
- **The body tint's key is `"body"`** everywhere — settings, spawn metadata, `OnlinePlayer._tints` — and its button says "Skin" only because "Body" is already the equipment column's label for the torso.

**Swapping the body swaps a node called `Character`, and the old one has to leave before the new one arrives.** Two siblings cannot share a name and Godot resolves that by renaming the one being added, so adding first left the player with a `Character2` and `_bind_character_nodes()` finding nothing — no meshes, no animation player, no skeleton for the weapon pose or the ragdoll, and a silent wall of null errors on every spawn.

### Weapons

Two weapons, both two-handed. Three files split the job: `weapons.gd` hangs the mesh off a hand bone at the right grip transform, `weapon_pose.gd` puts the arms where the weapon needs them, `laser_bolt.gd` is the projectile.

`weapon_pose.gd` is the interesting one: a `SkeletonModifier3D`, so it runs **after** the locomotion clip and overrides it, which is why you can sprint with a sword and the hold survives. `HOLDS` names, per hold kind, where each hand should be in sternum space, which hand the weapon aims from, its up hint, and how much the torso twists; `blade`, `rifle` and `rifle_aimed` are the entries. `SWING` is three keyframes over 0.62 s. `PITCH_FOLLOW` decides how much a hold follows the camera's pitch (rifle 1.0, blade 0.25). Arms are placed by two-link IK to those targets.

The player side: number keys address all five slots and the wheel stops only on filled ones; an empty slot holsters. Ammo is a fractional per-item `_cells` value that refills after `CELL_PAUSE` at `1 / CELL_RECHARGE` per second and is preserved across weapon switches. Right mouse blends FOV toward `AIM_FOV_SCALE` and halves look sensitivity. `_swing_weapon` and `_fire_bolt` are `call_local` RPCs, so the shooter and everyone else run the same code path.

### Which way is up

The world is a sphere, so **nothing in the movement code may say `Vector3.UP` or read `velocity.y`**. Three helpers in `player.gd` replace them and every line below them goes through one: `_up()` is the body's own up, `_flat()` splits a vector into the part along the ground, and `_rise()` is the part leaving it. Gravity, the jump, the stair probe, the slide, the fly lean and the clip picker are all written in those terms.

What makes them true is `_align_to_planet(delta)`, the first call in `_simulate_local_player`. It sets `up_direction` — which is what `move_and_slide` means by a floor — from the planet every frame, and turns the body to match. Every frame rather than only on landing, because *walking* is what changes it: a run across 500 m of an 8 km planet turns the local up by three and a half degrees, and nothing else would ever put it right. `_up()` then reads the body rather than the planet, because the body's frame is what `wish`, the stair probe and the camera are already expressed in.

**Turning the body is `rotate_object_local`, and `rotate_y` is a bug here.** Godot's `rotate_y` takes its axis in *parent* space: on a flat world that is the way up, and on a sphere it is the way up at exactly one point. Anywhere else, mouse-left/right tips the body off the ground instead of turning it on the spot. The radial alignment then hauls it back, so what survives of the turn is only the part of the mouse that happened to lie along the local up — at the landing site about a fifth of it — and out above the atmosphere, where nothing is hauling anything back, the body just tumbles. The symptom is a view that will not turn. `dev/_descent_test.tscn -- --yaw` measures it in ten seconds: turning has to move the view by the same angle in space as in air, and has to leave the body's tilt off radial where it found it.

**The body is only turned inside the atmosphere, and that gate is a correctness requirement rather than a matter of feel.** At the orbital spawn the planet is dead ahead and the way out of its centre is straight behind, so forcing up radial there leaves no tangent to keep the heading in: the projection collapses, the view whips 90° sideways, and the player spawns staring into empty space with the planet off screen. Out there nothing needs a floor anyway. `_alignment_blend` is therefore zero above `Planet.atmosphere_height`, ramps to one at the ground, and is scaled by how fast the flight is going — settling is what a float has time for, and hauling the body upright mid-dive fights the steering. Anything **not** flying returns one outright: it is on its way to the floor and needs the floor to be a floor. The turn itself is an exponential approach at `ALIGN_RATE`, so it reads as the planet taking hold rather than as a flick, and takes the same time whatever the frame rate.

**The planet's collider is not the planet, so the height field is what finally stops anything.** A chunk only gets a `ConcavePolygonShape3D` once it is near enough *and* finished building on the thread pool, and the budgets above widen that window on purpose — so there is always ground that is drawn but not solid.

Depth used to be a third condition and should not be: the soup was only built for chunks within two levels of `max_depth`, on the reasoning that a coarse chunk is never the one underfoot. It is, for the whole of an arrival. `_perf_test -- --arrive` casts 81 rays over a 200 m square half a second after landing somewhere new, and with that gate in place **all 81 fell straight through** (it is 0 of 81 now, at half a second and settled alike) — the drawn ground there is at depth 5, which had no faces to give a body, so the player passed through the surface they could see onto whichever deeper chunk was under it. Settled, the same 81 rays all landed either way, which is why nothing caught it for so long: the check has to be made *during* the arrival or the case does not exist. Building the soup unconditionally costs a rearrangement of vertices the build has already paid for, and buys the invariant that anything drawn can be stood on. `OnlinePlayer._catch_ground()` runs after every move and asks `PlanetShape.elevation` directly, in constant time and without a mesh, pushing the body back out to the surface and ending any flight that got there. `_descent_test` proves it by burying a flying player 120 m down where no collider exists at all and watching them come back up standing.

**It asks at `Planet.spacing_underfoot()` and not at `finest_spacing()`, and that is a correctness requirement rather than a saving.** The two differ only while the tree is still refining, which is exactly when this matters: every feature fades out at coarse spacing so it cannot alias, a canyon is nearly a step function, and so a chunk that has not refined yet draws a lid across the hole instead of the hole. Asked at the finest spacing under one of those lids, the guard reads a body standing on visible ground as thirty-six metres airborne — no floor snapping, no stair step, air control — and it sinks through onto the canyon floor. Asked at the spacing the ground was actually built at, the guard's surface *is* the surface on screen at every stage of the refinement. The readout prints the collider and the field side by side (`floor  mesh 0.1 m   field 0.2 m`) because their difference is the only thing that ever made this visible — settled, they agree to a few centimetres and there is nothing to see.

**`_near_depth` is the finest chunk drawn *over* the viewer, and it took three goes to be that.** The number is only worth having if it names ground the body is actually on, and the first two versions did not. It was the depth of the chunk with the smallest `chunk.distance`, which is wrong twice over: `chunk.distance` is the **lead** distance, aimed ahead along the path so ground about to be flown over refines before it is reached, so at speed it names a chunk nobody has got to yet; and `_distance` subtracts three quarters of a chunk's own width, which is right for deciding what to split and meaningless here, because a root patch is nine kilometres across and therefore reports zero from most of the visible cap and wins every comparison it enters. `_update_collision` had already been given the true position for the same reason and says so in a comment; the spacing pick never was. `_note_underfoot` now tests **containment** — the eye within the chunk's own arc of its origin — and takes the deepest of those, which is unambiguous because a parent and its children are never drawn at once. The sentinel is **-1 and not 0**, because depth 0 is a real floor at 785 m between vertices and falling back to unlimited detail under one is precisely the failure above.

**The guard is swept, not sampled, and at flight speed that is the difference between stopping and not.** `fly_speed` is 1000 m/s, which is nearly seventeen metres between one physics tick and the next. A point test at the end of that move cannot see a ridge narrower than the move: the body is over the ground where the tick began, over it again where the tick ended, and the hill it went through was never in front of anything that could look at it — no crash, no correction, no ragdoll, just a player inside the world. `_rewind_to_entry` walks the tick's chord in pieces the width of the field's own finest feature (`finest_spacing()`, about 1.5 m), halves the first piece that ends underground `SWEEP_REFINE` times, and puts the body at the crossing before the rest of the guard measures anything. A crossing found this way skips the two benefit-of-the-doubt tests below, because at the crossing the body is by construction *at* the surface and both would wave it through as a graze. `move_and_slide` does not need any of this — it sweeps its capsule — but at that speed there is nothing built for it to find. It is arithmetic and no physics query: **a height-field sample is 5.6 µs** at the finest spacing, so the whole sweep is a tenth of a millisecond in the worst tick and one length and a comparison in every walking one, where the chord is shorter than a piece.

**Where a chunk collider does exist, it wins**, and the order the guard asks in is the whole of it. The mesh is a triangulation of the same field, band-limited to whatever depth that chunk is at, so it sits up to a couple of decimetres below the value sampled here; it is also the surface the player can see. So the guard leaves the body alone while a collider is within `GROUND_MARGIN` (0.5 m) underneath, and overrides it only past `TUNNEL_DEPTH` (0.8 m), which is not a triangle that dips but a body inside the world. The earlier version of this had one margin doing both jobs and let the body sink half a metre before snapping it back — at 34 m/s² that is a bob three times a second, which is what "clipping into the terrain" looked like.

**`is_on_floor` is not the floor test here; `_grounded()` is.** Where no chunk body has been built, `move_and_slide` can only ever report airborne, and a body that believes it is falling gets air control, no floor snapping and no stair step — which is most of what "caught on every bump" is made of. So `_catch_ground` also sets `_footed`: within `FOOT_REACH` (0.35 m) of the field and not on the way up counts as having ground underneath, whoever is providing it. Flight and swimming are excluded, because both pass close to ground they are not standing on and both have their own tests for arriving. The capsule's `safe_margin` is 0.04 in `player.tscn` for the same family of reasons: a millimetre of slack is not enough for the solver to push a capsule back out of a face it ended up inside, on a triangle soup that is rebuilt under the feet as the detail changes.

**Arriving too fast is a crash, not a landing**, and `Stance.CRASH` is the fifth row of every enum-indexed table. Two things reach it: `_end_flight()`, which is the one funnel every way out of a flight passes through and so the only place that can tell the two apart without knowing which branch got there; and `_hit_something_solid()` after an ordinary move, which is what catches a fall off a mountain or a wound-up sprint into a cliff. Both judge on `_flight_velocity` or on the velocity kept from before the move, because **the collision has already spent the speed by the time it can be noticed** — reading `velocity` afterwards reports a landing every time. The threshold is `CRASH_SPEED`, comfortably above a hover so nudging a wall is still just a stop, and only `StaticBody3D` counts, so flying into another player floors neither of you.

`_end_flight` asks `_grounded()` and not `is_on_floor()` for whether there was anything to hit, and the distinction is the same one as everywhere else here: the collider is the thing that is reliably *missing* in this case. A flight fast enough to be worth crashing outruns the chunk builder, so the arrival that most deserved to put the player down was the one arrival with nothing underneath it to prove it had happened, and it set them gently on their feet at a thousand metres a second instead. For the same reason `_begin_crash` returns early if the stance is already `CRASH`: a hillside reaches it twice, once through `_end_flight` and once from the guard's answer back in the move, and a second pass would restart the timer and count the fall twice while the ragdoll, already limp, ignored it.

**A crash goes limp**, and `game/player/ragdoll.gd` is what does it. There is no ragdoll in the `.glb` — the Blender exporter writes a skeleton and clips, not rigid bodies — so `Ragdoll` builds one at run time from the rest pose: sixteen `PhysicalBone3D` bodies down `CHAIN`, each a capsule spanning from its bone to the named next joint, cone joints between them. Building from the rest pose rather than from a table means a change to the character's proportions carries through with nothing to keep in step. It is a `SkeletonModifier3D` added **after** `WeaponPose`, so it runs last and overrides both the clip and the weapon hold, and it costs nothing until something crashes: `active` is off and `_physics_process` is disabled.

Six things about it are load-bearing:

- **Gravity is applied by hand.** `PhysicalBone3D` has no `constant_force`, and the physics server's own gravity points down the global Y, which is out of the ground at exactly one spot on a sphere. So `gravity_scale` is zero and the player feeds `set_pull(-_up() * _gravity())` in every frame of `_crash_move`, which the ragdoll turns into a central impulse per bone.
- **The bones collide with the world and nothing else.** They are on their own layer with a mask of 1, plus a collision exception for the capsule they came out of. Self-collision on a chain this short is the usual way a ragdoll vibrates itself across a field; limbs passing through the torso is the cheaper of the two faults.
- **The capsule keeps sliding underneath.** It is still what the world collides with, and handing its position to a chain of rigid bodies would let a stray limb walk the player through a wall. Both start where the crash happened and both stop within a second, so they part by a stride at most.
- **The bones get the same ground guard the capsule has.** `_crash_move` hands over `set_floor(planet.global_position, _ground_radius)` each frame, and `_keep_above_ground` holds every bone's capsule surface at that radius. It is not belt and braces: a crash worth watching happens where the body just arrived at speed, which is exactly where the LOD's collider budget has not reached, and bones with nothing to land on go straight through the planet while the capsule stops on top of it. The radius is the one `_catch_ground` has already measured, so it is one sphere for the whole body rather than a reading per limb, which on ground coarser than the character is close enough. That is tidiness rather than thrift — a sample is 5.6 µs at the finest spacing, and sixteen of them a tick would not show — so a limb that needs its own may take one. The push is done in **velocity, never by moving a bone**: a body teleported out of the ground drags its joints and snaps the chain taut, and the write would be overwritten by the server's own sync in the same tick anyway.
- **Continuous collision is on, through the server.** A limb capsule is four centimetres thick and terrain is a triangle soup with none, so a bone falling at thirty metres a second crosses the ground and everything under it inside one tick. `PhysicalBone3D` does not expose the flag a `RigidBody3D` does, so it is set with `PhysicsServer3D.body_set_enable_continuous_collision_detection` on the bone's RID.
- **Getting up is `influence`, not a cut.** Over the last `CRASH_RISE` seconds `settle()` fades the modifier out, so the skeleton blends from where the body actually landed into the `Land` clip and the body rises out of its own pose.

The tumble in `_lay_out` is still there as the fallback for a character whose `.glb` arrived without a usable skeleton: `character`'s own lean pivot driven round at a rate taken from the whole impact — not from the speed left along the ground, or a dive straight down would stand bolt upright through its own crash. Either way input is ignored throughout, and the body gets up the moment the clock runs out and `_try_stand` finds room.

`dev/_descent_test.tscn` is the harness, and the numbers to beat: the orientation error survives untouched at 12 km, 6 km and 3 km, is half gone a few seconds into the atmosphere at 2.2 km, and is under a tenth of a degree by 300 m; a dive ends in the standing stance 0.01° off square; and a 245 m sprint that carries the body 1.74° around the planet finishes 0.16° off square with its altitude unchanged.

### The world

`game/world.tscn` is the planet, the sun and six spawn markers, plus the handful of things standing on the planet: the `LandingSite` anchor, a `CityBuilder` per town and the landmarks. There is no pause overlay — `GameMenu`'s Settings tab is the pause screen, and `GameWorld.set_local_pause()` is all that is left of the policy. The 32 m grass floor and its six primitive props are gone. **Nothing may sit at world scale beside the planet**: the LOD refines around the active camera, and the surface is 8 km away in every direction.

The spawn markers hang 17 km out, above the atmosphere on the day side, and players arrive there **in flight** with deliberately nothing under their feet, looking at a fully lit globe. Flying down and standing up on it is the opening move, and it works end to end — see "Which way is up" below for how.

`game/world.gd` spawns from the host's roster, cycles spawn points by peer id, handles pause (local only in multiplayer, real `get_tree().paused` in single player), and answers late joiners with a snapshot that includes what everyone is **wearing and holding**, not just where they are.

### The planet

The world itself, instanced in `world.tscn` and centred on the origin so a direction from `(0, 0, 0)` is a direction on the ground.

`game/planet/planet_shape.gd` is the terrain and the only copy of it: elevation, colour and normal for any direction from the centre. Sea level is exactly zero, so **anything the height field puts below zero is under water** — oceans, inland lakes and the lowland reaches of rivers are all the same one surface seen through different holes in the ground. Continents come from low-frequency noise biased at load so a requested `sea_fraction` actually comes out; mountains are cubed ridged noise masked to a separate roughness field, which is what allows genuinely flat plains at any altitude; rivers are the zero crossing of a noise field and lakes are basins on lowland flats, and both are simply carved out of the land.

**Half the land is arid country, and it is four ideas stacked on the ordinary terrain.** `aridity` is the one dial — at 0 the planet is the green one it started as, at 1 there is no grass anywhere — and `_arid_at` fades it in from the coast so a desert never reaches a beach. What it turns on:

- **Benches.** `_mesa` rounds the height onto multiples of `terrace_height` with a steep rise between courses, which is the whole of the mesa look. Every butte in sight of another has its courses at the **same altitudes**, because they come off one global ladder rather than anything local — that agreement at a distance is what reads as sedimentary rock, and no amount of noise produces it, since noise has no reason to agree with itself two kilometres away.
- **A plateau to cut them out of.** This is the line that makes it Utah rather than terraced mountains, and it is the one that took two attempts. Quantising a *ridge* gives a jagged crown, because a bench is only as wide as the underlying slope is gentle: at the full mountain term a course spans eighty metres and reads as crinkle. `_relief` therefore damps ridges and hills by `arid`, the desert becomes a broad uplift, and the same course spans a quarter of a kilometre.
- **Slot canyons.** `_river_cut` takes a second, far narrower threshold off the **same noise lookup** the rivers use, so the deepest feature on the planet costs no extra noise — and it is geologically the right place for it, since a canyon is what that river does to arid ground given time. Terracing runs *after* the carving, which is what gives a gorge the stepped walls it has in Canyonlands.
- **Hoodoos**, on the lip of a riser where they form. The finest thing on the planet and the first to fade, so they are only ever seen close up — which is honest, since at 1.5 m between vertices a spire is four vertices across and would be speckle at any distance. Gated hard and early: outside arid country, away from a lip, or at any coarse spacing, the lookup is never taken.

**Strata are a function of height alone, and `stratum_height` must not divide `terrace_height` evenly.** Terracing quantises the ground onto bench heights, so courses sharing a period with it put every bench top in the world on the same colour and the banding vanishes except on the risers — the first attempt came out a uniform salmon across a hemisphere for exactly that reason. Two more things were wrong with it and both are worth knowing: the rock colours are written **much darker than sandstone looks**, because the scene runs about 1.4 of light through a surface before ACES tone maps it, which is the same rule the city road tones are held to; and the flats keep most of their course rather than being buried in dust, because terracing makes bench tops the great majority of the ground and dusting them dusts the banding away with them.

`dev/_planet_test.tscn -- --tour` shoots `planet_mesa` and `planet_mesa_low` over the highest arid ground, and prints what share of the land is desert. Two ranges over one place because the two halves fail at different ones: benches read from the air, and the courses in a riser only resolve from close to. **Caves, arches and overhanging hoodoo caps are not in any of this and cannot be** — a height field holds one height per direction, the same reason an overpass has to be a road mesh. Those want scattered props on `SurfaceAnchor`, and `blender_assets/cave_room.glb` is already authored and waiting for it.

**The sea bed is two curves, not one, and the shape of it is the difference between an ocean and a flooded field.** `_sea_floor` runs a shallow apron out to `shelf_break` and then a slope into an abyss `ocean_depth` (480 m) down — deeper than the tallest mountain, which is the proportion that reads as an ocean. Two spans control how quickly each side of the waterline gets where it is going, and they are deliberately not the same number: land takes `CONTINENT_SPAN` (0.55) of the continent field to reach full height, the sea takes `abyss_span` (0.32) to reach full depth, because an ocean is a basin with a slope round its edge rather than a bowl. One curve at the land's span left the mean depth at 50 m with half the sea bed on the shelf, which is a blue surface sitting at sea level pretending to be the sea — the complaint that prompted all this. It now averages 211 m with two thirds of it past the shelf.

Both sides also **meet at zero**. The land's hill term does not start at zero — half its amplitude is a constant — so before the `ashore` fade in `_relief` the ground began at whatever the hill noise happened to read on the waterline, and every shore in the world was a step of up to `hill_height` with nowhere to wade in from. The sea bed's own relief is faded in with depth faster than it can grow, which is provable rather than tuned: it can never lift a shallow into an island the shoreline solver never counted.

`game/planet/planet.gd` decides how much of that to build. Each cube face is a quadtree that splits while the viewer is nearer than `split_ratio` chunk widths; chunk meshes are built on `WorkerThreadPool` and attached a few per frame, a parent keeps its mesh until every child has one, and leaves within `collision_range` get a `ConcavePolygonShape3D` whatever depth they are at. Vertices are stored around each chunk's own origin so coordinates stay small 8 km out.

**The detail is built around where the viewer is going, not where it is.** Ground takes real time to appear — queued, waiting for a slot on the pool, built there, then handed over a few per frame — and every bit of that happens after the viewer is already close enough to want it. Standing still that is invisible; crossing the ground it *is* the pop-in, because at 200 m/s the arrival is a second behind. So `_track_lead` measures the viewer's own velocity (nothing tells the planet what it is — it may be a player, a camera or a harness writing a transform) and `_refine` measures its distances with `_path_distance`, to the **segment** from where the viewer is to where it will be in `lead_time` seconds, capped at `lead_distance`. `_dispatch` orders the build queue by the same number, so the ground being flown into is also what the pool builds first.

Three things about the shape of that:

- **A segment and not a translated point.** Moving the centre forward costs nothing but coarsens the ground underfoot, which is the one place the detail has to be right when you stop. The capsule keeps both ends, so it degenerates to exactly the old behaviour when standing still — at rest the tour draws the same 639 chunks and 414k triangles it always did — and grows only along the direction actually being travelled.
- **`lead_time` is a time because what it covers is a latency.** `lead_distance` is only the cap that keeps `fly_speed` from asking for a kilometre of it; at 200 m/s the lead is 120 m and the cap is not in play, which is why the measured cost below is the realistic one.
- **Collision keeps to the true position.** `_update_collision` still measures from the viewer, because a collider is what the body stands on and leading it would take the floor out from under anyone who slowed down or turned. Ground ahead needs no body until it is reached, and by then its *mesh* — the part that takes time — is already built.

Measured on the 200 m/s crossing, the frame is a wash and the tail is better: mean 23.74 → 22.90 ms, p99 42.73 → 36.98, worst 48.69 → 40.16, and 1479 chunks built → 1157, because ground built ahead is still wanted when it is reached instead of being collapsed behind. What it costs is the planet's own CPU, 6.52 → 9.16 ms a frame, which on this scene hides under a frame that is GPU-bound elsewhere. `lead_time = 0.0` restores the old behaviour exactly, and is the first thing to try if a slower machine says otherwise.

**The render distance setting is `split_ratio` scaled, and it is the only knob in here that belongs in a menu.** The rest of the Detail and Budget exports trade one kind of hitch for another and want measuring, not choosing; `DETAIL_LEVELS` trades something a player can see for frames. What it moves is where the ground stops being sharp and not how much of the planet is on screen — the whole visible cap is always drawn, coarser with distance, and no level removes any of it. Cost is roughly the square of the scale, because it is an area of ground held at each level: 155k, 301k and 601k triangles from the air. The reach is taken once per walk into `_split_reach` rather than per chunk, since the walk is a thousand nodes of GDScript and the answer is the same for all of them.

**Three levels, because a fourth was measured and thrown away.** A 2.4 scale cost 1.1M triangles, doubled the collision bodies to 441, took the LOD walk to 2 ms and the worst frame to 17 ms — and could not be told from 1.6 in a photograph, from the air or standing on the ground. `-- --distance` prices every level at both vantages **and shoots each one**, which is the only reason that was knowable: a table of triangle counts makes a longer reach look strictly better, and the picture is what says nobody would see it.

**`Planet` and `PlanetShape` are both `@tool`, so the terrain is there in the editor too**, refining around the editor camera instead of a player — otherwise the node is an empty pivot and there is nothing to place a prop against. `PlanetShape` has to be a tool as well or it loads as a placeholder and `prepare()` cannot be called on it, which is the error to expect if the annotation is ever dropped. `editor_preview` turns it off for a scene only being opened to edit something else. Chunk meshes, colliders and the atmosphere shell are added with `INTERNAL_MODE_BACK`, which is what keeps hundreds of generated nodes out of the Scene dock and out of the saved `.tscn`; no collision is built in the editor, since nothing there walks.

Four things here are load-bearing and cost real time to rediscover:

- **Every read of the height field takes the spacing it is being sampled at**, and features finer than that are faded out rather than aliased. A river gorge is a near-step function; without this a chunk sampling every 25 m walks straight over one its finer neighbour resolves in full, and the two meet in a cliff tens of metres tall.
- **Relief is kept under a tenth of the radius.** A 500 m mountain is a serious climb at 1.45 m tall, but past that the silhouette stops reading as a sphere and starts reading as a potato.
- **The horizon is a property of the radius and nothing else.** At 8 km it is 165 m at eye height and 800 m from a 40 m hill. No amount of terrain tuning lengthens the view; only a bigger planet does.
- **Vertex colour alpha is how wet the ground is**, not an opacity. `PlanetShape` ramps it from `SHORE_WETNESS` at the waterline to 1 in the deeps, and `vivid_terrain.gdshader` reads "is this water at all" and "how deep" off it separately, so a shoreline can be smooth and bright without also being tinted like an abyss. A triangle spanning the shore interpolates across the band of damp sand between them. It now shades the **sea bed** rather than standing in for the sea, and the two together are not yet reconciled — the bed is still drawn as though it were the surface, under a surface. That is the next aesthetic pass, not a bug in either.

**To get the planet out as a mesh**, run `dev/_export_planet.gd`. Nothing in the game can be exported directly: the world is a height field, the quadtree only ever builds the chunks near the camera, and each of those is at whatever density its distance earned — so at any moment most of the planet is not geometry at all and the part that is, is a patchwork. The exporter samples the same field on a uniform grid over the same cube-sphere instead, one mesh at one density, the same one every run. Three things about it matter:

- **It reads the shape off the `Planet` in `game/world.tscn`**, so a bake is always of the planet in the game rather than of the defaults it started from, and it band-limits every sample to its own grid spacing the way a chunk does to its own. Sampling the true field at 49 m would alias every ridge in the world.
- **It mirrors `Planet._spread`**, and has to keep mirroring it. That is the tangent bulge that keeps quads near a face's corners the size of the ones in its middle; a bake mapped differently from the game is a bake that cannot be painted and brought back.
- **The six faces are laid out three across and two down in one square of UV space**, face `f` in column `f % 3` of row `f / 3`, with a `GUTTER` of unpainted cell edge so filtering and dilation do not reach into the neighbouring face. One texture covers the planet. The faces are not welded to each other — a vertex on a cube edge needs a different UV per face — but their positions coincide, so the seam is in the texture and not in the surface.

`--faces=N` sets the density: 256 is the default at 786k triangles and 49 m between vertices, 512 is four times that. The sea is baked as a separate `Sea` object at sea-level radius, because on a bake of the bare ground every coastline in the world is invisible — what marks one is the height the water comes to, not anything about the shape of the land. Output is gitignored: it is tens of megabytes and takes five seconds to remake.

### The sea

`game/planet/planet_water.gd` (`PlanetWater`), raised by `Planet._raise_water()` as an internal child at the planet's centre. There is exactly one of it and it is a sphere of exactly `shape.radius`, which is what makes every question about it a subtraction:

```gdscript
func depth_at(global_point: Vector3) -> float:
	return sea_level - global_position.distance_to(global_point)
```

That is the whole physics interface, and everything else follows from what it does **not** need. No area, no collider, no per-lake volume, no dependence on whether a chunk near the swimmer has finished building — the same reason `_catch_ground` reads the height field rather than the colliders. **The water is deliberately not solid**: flight goes through it, swimming happens inside it, and there is nothing to bump into.

**Drawn as one disc that follows the viewer**, bent onto the sphere by `vivid_water.gdshader` in the vertex stage under `world_vertex_coords`. A mesh of the whole sea fine enough to hold up from a beach would be millions of triangles, almost all of them over the horizon; this is nine thousand, always where they are being looked at. Three things make that work:

- **The disc is sized to the horizon**, `sea_level * tan(cap)` where `cap` is the angle of the cap the viewer can see. That is 320 m wading and 17 km from orbit, from one formula, and it is why there is no near/far mesh swap.
- **Rings are spaced by the square of their index.** The projection onto the sphere compresses the outer rings in angle, so a uniform grid would spend its detail exactly where the curve is throwing it away.
- **`depth_draw_always`, not `depth_draw_never`.** A transparent sea that writes no depth does not hide itself: the whole disc is drawn including the parts round the curve, and they pile up past the true horizon as a flat band with the rim's own polygons notched along the top. It costs nothing against the terrain, which is opaque and already drawn by then.

**The sea has no hard edge at the shore, and that is structural.** The waterline is where a smooth sphere crosses a triangulated height field at a couple of degrees, so it is not a line but a band many quads wide in which the ground rises above sea level and drops below it once per triangle. Drawn opaque to its own silhouette, that is a comb of teeth leaning along the triangulation's diagonal — worst from orbit, where the chunks are coarsest, and immune to any amount of tessellation on the disc, because the zigzag belongs to the surface being cut and not to the one cutting. So `shore_fade` feathers the water out over the last metres of its own depth, which removes the edge rather than smoothing it and is what shallow water does anyway. It is two terms because the band it has to cover is the mesh's excursion about sea level, which grows with LOD and therefore with range; the near term is held under `wash_depth`, or the feather thins the very water the surf's white wash is drawn on.

The surface is **geometrically flat** and the ripples are a normal perturbation only, because the swim and splash checks read sea level as an exact radius and real waves would put the water the player sees somewhere the water they feel is not. Ripples fade out past `ripple_far`, which is both an anti-aliasing measure and most of what the sea costs — beyond it the noise field is not evaluated at all.

**The surf knows where the land is without anyone telling it.** The opaque pass has already drawn the sea bed, so `vivid_water.gdshader` reads the depth buffer, turns that fragment back into a world position, and takes `planet_radius` less its radius from the planet's centre: the depth of the water column, in metres. Every white thing on the shore is a function of that one number, and since a band of constant depth *is* a line parallel to the coast, the foam follows every bay and river mouth exactly with no coastline ever being computed. See `shaders/vivid/README.md` for the three numbers that were each wrong once. It is also nothing to do with the sea's *physics*, which still knows only the exact radius — the surf is drawn where the water is thin, not where a wave is.

`splash(at, strength)` throws a one-shot `GPUParticles3D` burst that frees itself. Its spread is 180° on purpose: whether a `ParticleProcessMaterial` reads `direction` in the emitter's space or the world's is not worth depending on, and a burst thrown every way at once and pulled back by gravity is the shape either reading would give. **Gravity has to be worked out per splash** — it is a world-space vector, and on a sphere there is no one down.

### The weather

An iridescent cloud deck: a slab of air `Planet.cloud_thickness` metres deep centred on `Planet.cloud_height`, raised by `_raise_clouds()` beside the atmosphere shell and drawn entirely by `vivid_clouds.gdshader`. **There is no cloud object anywhere in the project** and nothing about the weather is generated in GDScript, stored or replicated. Every cloud is a function of position relative to the planet's centre, so the deck is located on the globe, is endless, and two players in different hemispheres see different weather with no wire traffic at all.

Four things are worth knowing before changing any of it, and `shaders/vivid/README.md` has the rest:

- **The sphere that gets submitted is not the clouds.** It sits at the slab's *outer* radius and its only job is to put a fragment on screen wherever the deck could be seen; each fragment then intersects its own view ray with the slab and marches the crossing. That is the whole difference between gas and a sticker — one sample per pixel, which is all a shell can take, has no thickness in it anywhere, so a cloud looks the same edge-on as face-on, has no underside, and passes through the camera as a wall with no inside. It also means flying into the deck starts the march at the eye, and cloud builds up around the camera on its own.
- **Condensing and evaporating are the same dial.** The density field holds still while the level it is cut at breathes: raise the cut and a cloud shrinks in from its edges until it is gone, lower it and it grows back out of its own core. A slow second field decides which part of the sky is doing which, so the deck never clears all at once.
- **The hue comes from three terms at three scales** — contour bands close up, the cloud's own body a few kilometres out, and `vivid_region()`'s colour wheel from orbit — each taking over as the one below it stops being resolvable. The bands need their own fade thresholds, several times tighter than the detail's, because they multiply the density's wobble by `iris_bands` and alias about that many times sooner. Fade them **out of the colour and never out of the phase**; see gotcha 26.
- **`coverage` is a share of the volume and not of the sky**, and the two are far apart: a shallow ray crosses kilometres of slab and several cloud cells, so the sky ends up about twice as covered near the zenith and totally covered at the horizon. Much above a third and the deck is a lid again.

The deck is one draw and its cost is all fill rate. A step leaves after three octaves when the fine ones could not have made it cloud whichever way they landed, which is a bound derived from `detail_relief` and not a guess; most steps of most rays leave there. Measured against the same run with `-- --noclouds`, it costs 0.04 ms from orbit, 0.2 ms at treetop and 0.36 ms standing, but **2.3 ms at 1800 m**, where every pixel is a ray skimming along the slab instead of dropping through it. That one stop is the number to watch; `march_steps` is the budget and the only dial that bounds it.

The step is sized off how fast the field turns over **along the ray**, never off the deck's depth — the field packs `vertical_scale` turns into 700 m of slab and `cloud_scale` turns around a 9 km sphere, so a ray dropping through needs several times the sampling of one skimming along, and sizing both the same spends the whole budget on the skimming case. It also grows by `step_growth` each step, so a fixed budget reaches ten kilometres instead of three.

There is deliberately **no jitter** on the first sample. The usual dither wants a temporal filter to resolve it and there is none here; at these step sizes it stops dithering and becomes the noise.

Three transparent shells now sit around the planet and their order is written down rather than sorted: `render_priority` is 0 on the sea, 1 on the clouds, 2 on the air. Godot sorts transparency by the distance to each object's origin, and the sea's origin is the patch of water under the viewer while the other two are at the planet's centre — so from orbit the sea sorts nearest of the three and is drawn over the clouds above it.

#### The snowfall

`game/planet/snowfield.gd` owns everything the polar cap does that is not the shape of the ground: the snow falling through it and the boot prints left in it. Like `PlanetWater` it is one node raised by `Planet` at the planet's centre, standing in for something that covers a region, and **where the arctic is is not decided there** — `PlanetShape.frost()` owns that and the snowfield only asks. `dev/_arctic_test.tscn` measures it, and the snow is the part of it that can be wrong while every screenshot looks fine.

**The flakes are sown through the whole column, not released from a slab at the top of it, and that is the one thing here not to tidy up.** A slab is the obvious shape and it is correct only for a viewer standing still: the air around the eye is then filled by *transit*, and transit from eleven metres up at 2.6 m/s takes four seconds, in which a walker covers more ground than the box is wide. So the fall was a snowfall for as long as the player stood in it and about a dozen stray flakes the moment they walked — 2.6% of the frame against 0.5%, and both shots looked plausible alone. The harness now measures **standing and walking** and fails if the walk keeps under 60% of the stand; it reads about parity.

Two numbers follow from that and are joined at the hip. A sown volume gives a column that thickens downward — the flake count crossing any height is what was released above it — so the fall is uneven over the `FALL_SPEED * FLAKE_LIFE` metres a flake covers in its life. Hence a **short life and a box taller than the view needs**: at 1.5 s the ramp is spent in the 3.9 m of air above `FALL_TOP - 3.9`, and everything from there down to the ground is even. The same short life is what refills the box behind a viewer who has just moved, so `FALL_SPREAD / FLAKE_LIFE` — about 7 m/s — is the speed the fall keeps up with, and it thins gracefully above that rather than emptying. `FLAKE_FADE` is not decoration: a flake sown in mid-air and taken away again in mid-air pops visibly within a couple of metres of the eye, and it rides on the process material's `color_ramp`, which a `StandardMaterial3D` **silently drops** unless `vertex_color_use_as_albedo` is on.

There used to be a 2.5 m dead zone on moving the emitter, on the grounds that writing a world-space emitter's transform resets its emission and reissues the live flakes where they started. **It does not** — the same walk measures 0.5% of the frame with the dead zone and 0.7% without — so the box now follows the eye every frame, and the dead zone was only ever buying a fall that lagged the viewer by up to its own width.

#### The terrain is native, and `PlanetShape` is its front door

`game/planet/planet_shape.gd` still owns the planet: the exported numbers, the towns, the shoreline solve and every method anything else calls. What it no longer owns is the arithmetic. `native/src/planet_field.cpp` (`PlanetField`, a GDExtension) holds the nine noise fields, `elevation`, `color_at`, `sample` and the whole of a chunk's mesh build; `PlanetShape.prepare()` builds one, hands it every tuning number through `native_settings()`, and each public method is now a call into it plus the town override.

The split is there and not somewhere tidier because **a town is not terrain**. A `CityPlan` is a baked raster and a pad written in GDScript, so pushing the boundary any lower would mean porting the cities too; leaving it any higher would mean the native field could not build a whole chunk. So the seam is drawn exactly at "everything that is a function of a direction and a spacing".

Four things about it are worth knowing:

- **`_field` is typed `PlanetField`, and that is a performance requirement.** Held as an `Object`, GDScript resolves the call by name against `ClassDB` every time, which takes a global read lock — four build threads asking a few thousand times a chunk made a sample that had just got cheaper twenty times dearer, and the symptom was the entire terrain pipeline stalling rather than a function looking slow. A bare bound call is 0.028 µs typed against 0.194 µs untyped.
- **A chunk is built in one call.** `Planet._build_natively` hands `build_patch` the face basis, the chunk's square and the skirt, and gets vertices, normals, colours, UVs, indices and the collision soup back. The GDScript version of the same loop is kept and is not dead code: it is the path a chunk **over a town** takes, chosen by `PlanetShape.overlaps_town()`, which is deliberately conservative so it can only ever err toward the slower path.
- **The palette and the named constants are passed across, not duplicated.** `native_settings()` sends `CONTINENT_SPAN`, `RESOLVE_FLOOR`, `SHORE_WETNESS`, `ICE_TOP`, `SEA_ICE_WETNESS` and all thirteen biome colours, so `planet_shape.gd` stays the one place the planet's palette is written down. Literals on the C++ side were the first version and they are the obvious way for a colour to be changed in one file and not the other.
- **`dev/_field_check.gd` is the proof, and `dev/field_reference.json` must never be regenerated.** The baseline was taken from the GDScript field before any of it was ported, and it is committed rather than left in gitignored `dev/captures/` for that reason. The check compares all nine noise fields, `elevation` at six spacings and `color_at`, sample by sample over 4096 directions: **worst error 0.000000000 on every one.** Refreshing the baseline from the thing it is checking turns the only evidence the planet did not change into a tautology.

Two bugs the check caught that no screenshot would have. `color_at` used to return water *before* the town loop, and the composed version ran the loop over every colour — so the Landing's harbour was being tinted with zoning concrete, in 3 samples of 4096. And the first cut of the port disagreed on 45 heights, which looked like a subtle noise mismatch and was actually the separately-instantiated field in the harness having solved its own `sea_bias` over a different sample count. Both were single-digit sample counts out of thousands, both would have rendered as a perfectly plausible planet.

**What the port was and was not worth.** A sample went from 4.73 µs to 1.79 µs — 2.6x, not the ten the exercise was started for, and the reason is that **the noise was always native**: Godot's `FastNoiseLite` is C++ too, so what was ported was the glue around 28 noise octaves, not the octaves. The large win came from somewhere else entirely, and only became visible once the sample was cheap: a chunk went from 9.4 ms to 0.89 ms, because 90% of it was never the field at all but the GDScript grid loop around it — 361 vertices at 26 µs each. **Measure the loop before porting the function inside it.**

#### What the planet costs, and why it is cheap

Standing still the LOD does nothing; the case that matters is crossing the ground at flight speed, and `dev/_perf_test.tscn` drives exactly that — a **fixed** 200 m/s at 80 m, position written directly rather than flown, because a flight model that winds its speed up over seconds makes a stuttering run fly slower and therefore stutter less, and a benchmark whose load depends on its own result cannot be compared with anything. It reports a median and a p99 alongside the mean, and breaks the planet's own update into refining, queueing, drawing, colliders and mesh uploads. That crossing went from a median of 38 ms to 1.3 ms, and from dropping four frames in five to dropping none in eleven thousand, while drawing the same 650 chunks off the same 930-node tree. Five things did it, and the first is worth more than the rest together:

- **`pending_limit` is 12, and everything written about it before the native port is now wrong.** It was 4 because a build was a few hundred GDScript samples and twelve at once starved the main thread badly enough to cost 35 ms a frame on a 24-core machine — true then, and the reason the paragraph above ends "anything wanting more ground per second has to make a build cheaper". That is exactly what happened: a build is 0.9 ms of native code against 9.4 ms of interpreted, so twelve now cost less CPU than four did. It is also a **throughput ceiling and not only a concurrency cap**, which is the part that hid the problem: finished tasks are collected once a frame, so the pool can never deliver more than `pending_limit` chunks per frame however cheap a build gets. At 4 that is 240 a second at 60 fps — and arriving somewhere new was converging at exactly 240 a second while the workers sat 95% idle. Twelve rather than the twenty-four that converges fastest, because past about there the extra supply goes on churn: the 200 m/s crossing built 8400 chunks at 24 against 5960 at 10, for the same ground and the same 816k triangles standing still.
- **The quadtree is walked 30 times a second, not once a frame.** Two passes over a thousand nodes is a few milliseconds of GDScript, and at 300 fps that was most of the frame for decisions that do not change between frames 3 ms apart. Finished meshes are still attached every frame, because that part is a tenth of a millisecond and it is what puts new ground on screen.
- **Dispatching is every frame too, and for exactly the same reason.** It costs 0.14 ms and it is what keeps the pool fed; run only on the walk, a build slot that came free just after one stood idle until the next, up to 33 ms later. That measured as **2.5 of 4 slots busy and the pool full only 61% of the time, with 43 chunks queued waiting to use the other 1.5** — idle builders and a backlog at once, which is the signature of demand arriving too late rather than of capacity running out. Requests outlive the walk that found them, so there is always a list to fill from; the walk dispatches again afterwards on its own fresher list.
- **Nothing splits until it has been built.** Splitting on distance alone let a viewer at 200 m/s demand levels far faster than the pool could supply them, growing a tree of thousands of meshless nodes that every pass then had to walk.
- **Splits and collider builds are budgeted per frame** (`splits_per_frame`, `bodies_per_frame`). `ConcavePolygonShape3D.set_faces` builds its BVH on the main thread, so a collider is a main-thread cost like a mesh upload and is paid in instalments for the same reason. A body measures 0.45 ms, and `bodies_per_frame` is 8 because that is what drains the backlog after an arrival in about three seconds rather than seven; the `floorless` figure in `statistics()` is that backlog, and a steady non-zero reading there is ground somebody can fall through.
- **The split budget is spent nearest-first, and the walk only nominates.** `_refine` collects candidates into `_splitters` and `_grow()` spends the budget on the nearest of them afterwards. Splitting where they are met spends the allowance in *tree* order, which has nothing to do with distance: eight splits a walk went to whatever the recursion reached first, so ground already behind the viewer took the frame's whole allowance while the chunk under their feet waited for a later walk to come round to it. `_dispatch` had this argument written into it from the start and the split half did not.
- **The tree stops growing while the queue is hopeless** (`QUEUE_DEPTH`, eight times the pool's width) **and the pool is flat out** — both conditions, and the second is easy to leave off and expensive to. A split makes four meshless chunks, and while hundreds are already waiting *and every builder is busy* the ground they describe cannot arrive one moment sooner for having been asked earlier; all four do is lengthen every later walk. Ungated, that feeds itself: a bigger tree costs more per frame, so fewer meshes are attached, so more of the tree is meshless. But **a deep queue on its own is not evidence of anything** — it runs 80 deep in the healthy case, well above any fixed mark worth setting, so gating on the queue alone throttled the tree while slots stood empty. The loop is self-limiting rather than tuned: builds landing take chunks out of the queue, the queue falls under the mark, splitting resumes.
- **`splits_per_frame` is 26 and the budget is spent by repeated linear scan, not by sorting.** Sorting once and taking the front is strictly better on paper — a few thousand comparisons against tens of thousands of array reads — and measured worse on both counts, refine 6.25 ms to 8.51 and delivery 2856 chunks to 2618. `sort_custom` pays a **script call per comparison**, and one of those costs more than the dozen inline array reads it saves. `_dispatch` scans for the same reason at a much smaller budget. Do not re-derive this from the complexity: the constant is what decides it.

Together with the cheaper build, the 20 s crossing at 1000 m/s went from **1009 chunks delivered to about 2750**, with the queue no longer starving the pool and the median frame down from 61.9 ms to 26 ms.

#### Arriving somewhere new, which throughput does not measure

`-- --arrive` is the second question and the one a player actually complains about: it lands the viewer somewhere with nothing pre-built and reports the depth of the drawn chunk **under their feet** every half second until it reaches `max_depth`. Throughput says how much ground is being built anywhere; this says whether any of it is where somebody is standing, and the two came apart badly — the crossing figures nearly tripled while arrival did not move at all.

It also casts a **floor probe**: 81 rays straight down over a 200 m square, once half a second after arriving and again once everything has settled, each compared against the height field the same ray should have hit. That is the only check here that is not about time, and it is the one that found the collision gate — a hole in the floor is invisible to a depth ladder, to a chunk count and to a screenshot, and shows up only as a body passing through a surface it could see. The two readings have to be looked at separately: the settled one has passed for as long as it has existed, and the fault lived entirely in the other.

**The headline number is that the ground underfoot runs at depth 4.7 of 9 while flying at 1000 m/s.** You do not arrive with detail and lose it; you arrive four levels coarse and then watch it climb, which is exactly what "the terrain changes as I walk around" is. Converging those levels is **956 chunk builds**, and that count is invariant — it is the same 956 whatever the budgets are set to, because it is simply the ground within the split radius at each level.

That invariance is what makes this tractable to reason about: arrival time is 956 builds divided by the rate they can be produced, so **only two things can ever move it — the cost of a build, or the number of chunks a level needs**. Everything else that looks like a dial has been measured and does nothing:

| Tried | Result |
| --- | --- |
| `pending_limit` 8, 12, 16 | **Worse**, and never converged. Confirms the contention rule below; 4 stands. |
| `applies_per_frame` 16, 40 | Nothing, to two decimal places. |
| `lod_updates_per_second` 60, 120 | Nothing, and 120 is slightly worse. |
| `lead_distance` 2500, 6000 | Nothing: depth underfoot stays 4.7. The pool is already flat out, so leading further changes *which* ground is built and not how much. |
| Relaxing `queue_depth` to 40+ | **Collapses to depth 2** — see below. |
| A floor under the throttle | Same collapse. |

`splits_per_frame` is the exception and it is not monotonic: 8 gives 7.0 s, **26 gives 3.8 s**, 50 gives 7.0 s again. Both ends fail for the same reason as the collapse, so treat 26 as a measured optimum and re-measure rather than reason about it if it is ever moved.

**Letting growth run is the trap, and it fails in a way that looks like a rendering bug.** `_show` cannot draw a level until all four of a parent's children have meshes, so coverage — never depth — is the quantity that matters. Growth spent nearest-first buys a single deep *chain*, because the nearest child of the nearest chunk is nearest again; its siblings never arrive while the pool is busy, the spike covers nothing, and the ground underfoot falls back to whatever shallow ancestor is whole. Measured at **depth 2, held for the full eight seconds**, from both obvious ways of letting growth run. The tight queue mark is not really protecting throughput at all: it is forcing breadth-first growth by accident, by stopping splits until a level finishes. Gating a split on its siblings having meshes was tried as the honest version of that and did not help either — it made the first two seconds *coarser* — so the accident stands.
- **A chunk's normals are a central difference of its own height grid, not the field's gradient.** `PlanetShape.normal_at` is four more evaluations of the entire height field per vertex, and profiled at full depth that was **23.4 µs of the 30.4 µs a vertex cost** — 77% of a build, spent on a gradient the build could read off numbers it already had. `_grid_normal` differences the neighbouring grid samples instead, and the crossing went from 1243 chunks delivered to 1775 with the median frame down from 61.9 ms to 44.5 ms. The normal is also the more honest one: it describes the triangles being built rather than a finer surface this mesh has not got the vertices for. Against the old normals the whole frame differs by a mean of 0.7 of 255, so this is a cost change and not a look change.
- **That is why the grid steps one cell outside the patch.** The ring used to be a copy of the patch edge; it is now a real sample beyond it, so every vertex including the edge ones gets a *central* difference. Clamp it instead and each side of a chunk boundary takes a one-sided difference in the opposite direction, which disagrees with its neighbour and seams down every chunk edge on the planet. The ring is still only differenced, never stood on — a skirt vertex takes the patch edge's direction and height and drops them, so the curtain and every other vertex are exactly where they always were.
- **A new chunk inherits its parent's ground level instead of sampling for its own.** One height-field sample costs about a third of a millisecond and a split wants four. The build corrects the value on its worker thread, and since a chunk cannot split before its build lands, its children always inherit a measured number.

**A chunk build is `PlanetShape.elevation` a few thousand times and essentially nothing else, so that one function's cost is the arrival time.** It is **4.7 µs** a sample, about 5 ms for a 1089-vertex chunk, and getting there from 6.7 µs took 30% off arrival. Two things did it, and both are the same lesson — **GDScript charges far more for reaching a function than for the arithmetic inside it**:

- **The towns are tested inline.** `CityPlan.near()` is two comparisons and a dot product, and *calling* it cost 0.82 µs of a 6.7 µs sample — 12% of every height on the planet spent on cross-resource call overhead. `prepare()` now flattens the test into `_town_up` / `_town_cap`, one row per town in `cities` order, with an unreachable cap standing in for a town that is switched off so the indices cannot shift.
- **`_resolves` is written out at its eight hot call sites.** Up to eight land on every sample. Its `spacing <= 0` guard was always redundant — a weight below both ends of a descending `smoothstep` returns exactly 1.0 — so the inlining is provably identical, and the function is kept for the readable statement of the rule.

For scale when judging the next candidate: **one noise lookup is 0.24 µs**, so a sample is about twenty of them, and `frost` is 0.29. The arid terrain of §2 is *not* on this bill — 6.52 µs with it against 6.60 without, because its gates are taken before its lookups are.

**"It loads late" is a supply question, and the harness now prints the two numbers that answer it.** The `build pipe` line reports how many pool slots are busy, what share of frames the pool was full, and how deep the queue got. Together they say which end of the pipe is narrow, and the two ends want opposite fixes: a full pool with a long queue is **supply**, and free slots with a queue is **demand asked for too late to use them**. Chasing the second when it was the first is how the lead below got built first and did not fix the complaint. `--speed=` drives the crossing at something other than 200 m/s, which matters because the two ends fail at different speeds — the frame cost is worst where the tree is deep, and supply runs out where ground arrives faster than it can be built.

**Frame times off this harness are only comparable within one run.** On the development laptop the *identical stationary* stops came back 5 to 10 times slower in a run started minutes after another, with two thirds of the frame outside the planet's own update — sustained load throttles the machine, and the bench moves further between runs than most changes being measured do. Chunk counts, queue depths and node counts are set by the control loop rather than by the clock and stay comparable; milliseconds do not. Interleave the A and the B, or measure a ratio.

Turning the last four off while leaving `pending_limit` at 4 still drops no frames, but costs about 3.4 ms a frame of headroom — which is the budget the towns are going to want. The sea has since taken a share of it and it did not show: one draw of nine thousand triangles, with the ripple noise switched off past `ripple_far` so the fill cost is bounded to the water near the camera rather than to the water on screen.

`Planet` also raises the cloud and atmosphere shells — both go up through one `_shell()` helper, since they are the same object at different radii with all of their appearance in the shader. The cloud shell's mesh radius and the shader's `shell_radius` **must be the same number**, and `_raise_clouds()` sets both from one expression for that reason: the sphere is the volume's silhouette, so a mesh smaller than the field clips the deck at the limb and a larger one bills for empty sky. `Planet` also publishes the shader frame every process, guarded on change: a global shader parameter counts as a uniform change, and the sky's radiance cubemap — which is the scene's ambient light — is rebuilt whenever one moves. The shell's `shell_height` and the sky's `atmosphere_height` **must match**; below that line the sky draws the haze and above it the shell does, so a mismatch shows as a band of altitude with either no air at all or twice as much.

### The cities

Two towns, in `game/city/`: **Vacationer's Landing**, 1.8 km of graded coastal ground on the hemisphere the spawn markers look at, and **Meridian Flats**, a level upland pad 38° round from it in the sunlit belt. Each is four separable pieces — the ground it stands on, the colour of that ground, the roads on top, and the markers that find it from space — and only the first is structural.

**No file knows about more than one town.** `Settlements` is the registry: a `StringName` per site, and the `CityPlan` and `RoadNetwork` behind it. `PlanetShape.cities` is a list it fills, `CityBuilder` is one node per town naming its `site`, and every layout table lives in its own file. Adding a third town is a new layout file, a line in `Settlements`, and a node in `world.tscn` — nothing existing gets edited, which is the whole point of the split.

**The pad is in the height field, not a mesh over it.** `PlanetShape.elevation()` is the single source of truth for the chunk meshes, the chunk colliders, `SurfaceAnchor` and the player's ground guard `_catch_ground()`; a plane laid over the terrain would leave all four disagreeing, and the guard would keep hauling the player down to the hills underneath. So both hot functions walk `cities` and take one dot product of an early out per town — 1.4 µs a sample off every pad, 3.8 µs on one.

`PlanetShape.settled` is the switch that turns the towns off, and anything measuring raw terrain wants it clear: the site finder and the planet export both do, because a search for flat ground that counts the pads finds the pads.

Two consequences follow from being on a sphere:

- **"Flat" is constant elevation, not a Euclidean plane.** Gravity is radial, so a spherical cap at one height is what reads as level underfoot. A true plane 1.8 km across would stand 51 m proud of the sphere at its rim.
- **A pad may be graded or level, and which one is a siting decision.** The Landing is graded, 12 m at the shore to 90 m inland at a peak of 8%, because that site is a natural amphitheatre and cutting it flat meant an 80 m cliff along two sides; `GRADE`'s seven knots are smoothstepped between, and only the inland coordinate is read, so the city is level across its width and terraced along its length. Meridian Flats is one knot and therefore dead level at 119 m, which is what the site was chosen for — `dev/_city_site.gd` searched for ground already flat enough to take a level pad without a cliff at its rim.

`CityPlan` owns the local frame: azimuthal-equidistant both ways, so a road written as 1800 m long is 1800 m of ground. `prepare()` bakes the zoning into one 256 px raster over the town's own cap, painted district by district over its own bounds rather than pixel by pixel over every district, and `tint()` mixes it over the biome colour with the same weight the pad height uses — so the colour and the ground end at exactly the same place. The raster is read-only afterwards, which is what makes it safe on the mesh worker threads.

`CityPlan` is a plain `Resource` with every one of those numbers exported, and the layout files are static factories that fill one in. That is why two towns can differ in size, grade, reach and palette without a branch anywhere: the plan is data, and the only thing that varies per town is who wrote it.

Roads go **on top**, as one mesh, and that is also the only way to have elevated ones: a height field holds one height per direction, so an overpass cannot exist in it. Standing on a road 0.1 m above the pad puts `under` at −0.1, inside the guard's `FOOT_REACH`, so it leaves the player alone; on a deck 9 m up the guard returns immediately and the deck's own collider does the work.

A layout file is the authored town and nothing else: `DISTRICTS` as rounded boxes and discs, `KINDS` as widths and tones, and the streets as a **junction graph** — `JUNCTIONS` names points, `ROADS` names chains of them. That is what makes "roads don't disconnect" structural instead of hopeful: two roads meeting at a junction share the exact same point by construction. The Landing comes to 97 junctions, 69 roads and 30.8 km of street with nine intended dead ends; Meridian to 61 nodes, 25 roads and 13.5 km with three.

Four of the Landing's roads read oddly until you know what they are avoiding, and all four are the crossing audit's doing. The ring road takes a node at `ll_hb` to go round the **outside** of the harbour block, because the straight run from `ll_sw` to `sd_w` lies along Crane Street and then over the mouth of Dock Road. Marine Parade stops at the Strand's east gate rather than carrying on to the shore, which is Strand Shore Gate's leg. The Strand runs **through** `vb_1` because it passed two metres from it. And the Kestrel and Juniper closes hang back into the block between the collectors, because the strip between Collector B and the ring is 60 m deep and both of them used to end outside the ring altogether.

**The line pass comes first, and it is a separate object.** `RoadNetwork` takes the graph and the kinds and does everything that is not geometry: tessellate each chain to 10 m stations with quadratic Bézier bends, decide which nodes are really junctions, take each junction's setback out of the centrelines either side of it, and hand back `traces` (whole) and `runs` (cut). Nothing in it draws, so it can be **read, drawn and audited before a triangle exists** — `dev/_city_test.tscn -- --lines` photographs exactly the lines the mesh will be swept along.

`RoadNetwork.audit()` is what the line pass is for. It flood-fills the graph, names any junction cut off from the rest, finds blocks whose street was eaten by the setbacks at both ends, and looks for roads laid through each other with no junction between them. **It found ten of those in Vacationer's Landing the first time it was run** — a layout that had been looked at in a hundred screenshots — which is the argument for the whole line pass in one sentence. Two rules learnt the hard way:

- **Test the tessellated lines, not the chords between the nodes.** A segment with a `bend` bows away from its chord by the bend itself, so chord-testing reported nineteen crossings in a town that has ten — nine of them curves clearing another road by tens of metres.
- **Centrelines that cross and ribbons that graze are different faults.** Crossing is an error in the table; grazing is a road built too close to another and is reported apart from it. A junction both roads are named on excuses a meeting near it, because two arms leaving one junction at an acute angle keep overlapping well past the paving — that overlap *is* the junction, seen from further along.

`RoadMesh` sweeps a resolved network into 19–50k triangles in a single `MeshInstance3D`, with parapets, soffits and piers under any elevated run. Tone is vertex colour throughout, which is why one material covers asphalt, paving, deck and pier. Collision is a `ConcavePolygonShape3D` per 300 m tile, so the broadphase culls by AABB instead of testing the whole city. It takes a `CityPlan` and a `RoadNetwork` and knows nothing about which town it is building.

`RoadProfile` owns the cross-section, and it exists because two things need those numbers and must agree: the mesh extrudes them, while `RoadNetwork` wants only the outermost offset, to know how far back from a crossing a road has to stop. When those disagreed the junction paving either floated clear of the roads reaching it or overlapped them, and neither shows in a picture of one road.

**A raised roadbed is a walkability constraint before it is a look.** `OnlinePlayer` steps up `step_height` 0.3 m and treats anything past `floor_max_angle` 45° as a wall, so Meridian's two-foot lift can only be got onto up a ramp: `RoadProfile.apron()` grows that ramp from the road's own fall to hold `RAMP_GRADE` (30°, leaving margin — at 45° a body arriving with sideways speed slides back off). The fall is **not the lift**: a kerbed road's outer surface is its footway, a kerb higher again, and sizing the apron from the lift alone built a 36.7° ramp where the table said 30. Nothing but walking off a boulevard in the harness and measuring what was underfoot would have caught it, which is what `_walkable` now does for every kind — worst rise between samples 0.25 m apart, and whether the apron's lip reaches the ground where the profile says it should.

**A road is cut back before every crossing and the crossing is paved separately**, which is the part that is not obvious and the part that was wrong first time. Sweeping a road straight through its junctions is simpler and produces three faults at once: each road's footway is a raised kerb-height strip laid across the other road's carriageway, the four corners of a crossroads are left as bare ground because neither ribbon turns, and the pad filling the middle sits at exactly carriageway height for the depth buffer to argue with. So `RoadNetwork._survey` decides which nodes are real junctions, `RoadNetwork._cut` takes that junction's setback out of each centreline either side of it, and `RoadMesh._pave_junctions` builds the crossing from the **rings the ribbons actually stopped on** — not a fresh cross-section at the same place, so the two surfaces share their corners rather than merely being flush. Between one road's left rim and the next road's right rim goes a mitre column standing where the two kerb lines would have met, which is what carries the footway round the corner. A node with one road is a cul-de-sac and gets the same treatment as a semicircular head.

Three consequences worth knowing before touching it: a node the same road passes through twice and nobody else touches is a **bend, not a junction**, and cutting there would only put a seam where the sweep already turns smoothly; the setback is clamped to 35% of the shortest street at that junction, so two junctions can never eat the road between them; and viaducts are swept whole and excluded from the survey, because they cross at nine metres and meet nothing at grade except where a ramp runs down into a road.

**Meridian Flats is deliberately not shaped like the Landing**, and it is the town to test the road code against for that reason. Where the Landing is a coastal fan of curving collectors following its terrain, Meridian is orthogonal: a rounded-square ring road, two axis boulevards crossing at a central plaza, and a downtown grid **rotated 30° inside them** so that every grid street meets the ring and the diagonals at an acute angle. That is the hard case for mitred junctions, and it is why the grid is turned rather than aligned. Around it are a nightclub strip of one-lane back lanes, two residential crescents with cul-de-sacs, and a park crossed by paving-tone paths and promenades on a lower 0.22 m lift, since a path is meant to be stepped onto rather than ramped up. Its six waypoints come from `MeridianLayout.WAYPOINTS` and are raised by `CityBuilder` itself, so there are no landmark nodes for it in `world.tscn`.

Two things about how it looks:

- **`city_road_surface.tres` switches the region wheel off** (`region_albedo = 0`). That wheel is what gives the planet its bands of hue, and concrete that picks up a rainbow is not concrete. The zoning under the roads is terrain and does still take it, which is why the districts read as vivid from the air.
- **Road tones are darker than they look in the file** because the scene runs about 1.4 of light through them before ACES tone maps the result. `ASPHALT` at 0.16 is mid grey on screen. Judge a tone under `dev/_city_test.tscn`, which copies the sun and environment out of `world.tscn`, and nowhere else.

### Waypoints

`Landmark` extends `SurfaceAnchor`, adds a `title`, a `tint` and its three ranges, and joins group `landmarks`. `WaypointLayer` sits on the player's HUD, walks that group each frame, and draws a diamond and two lines of type at `unproject_position()` — pinned to a screen-edge margin, with the diamond stretched into a pointer, when the target is off screen or behind. It hides with the reticle when a menu opens. Five places are named in `world.tscn`: Vacationer's Landing, Farlands at the antipode of the spawn markers, Iceland and Goblinworld on the poles, and Nightcity on a coast in the permanent night side.

**A marker is type with an ink outline and no plate.** Everywhere else in this game, text over the world sits on an opaque `Style.HUD` plate, for the good reason in §1 — but that rule was written for one or two fixed panels, and five plates hanging in the sky at once is not legibility, it is furniture. `outline_size` does the same job for free: it costs no area, and unlike a drop shadow it survives both the pale sky and the dark sea. Anything new that draws *many* labels over the world wants the outline; anything drawing *one* still wants the plate.

**All three range rules exist to get the marker out of the way, not to make it visible.** `show_beyond` hides a name once you are close enough to see the place; `aimed_beyond` — used when the landmark is inside a few degrees of the crosshair — hides it a good deal sooner, because looking straight at somewhere is the strongest possible statement that you have found it; and `hide_beyond` is the outer edge, past which nothing is named at all. Raise them rather than adding a fade if markers feel intrusive; all three are per-landmark exports, and each is faded over `FADE` (0.3) of its own value so a marker arrives rather than blinks.

**The planet is approached unlabelled, and the default `hide_beyond` of 4500 m is what does it.** The spawn markers hang 9 km up, and from there the whole lit hemisphere is in frame: naming it is a contents page rather than a view, every place there is at once, over ground too small to put a name on. So the outer edge is half that descent — nothing is named from orbit, and the names arrive on the way down as the ground under them turns into somewhere. It is worth knowing this is a **default rather than a scene value**: a landmark that should carry further has to say so, and `hide_beyond = 0` switches the outer edge off entirely.

**The three ranges are one setting, not three.** `aimed_beyond` has to stay well under `hide_beyond` or the two close on each other and an aimed marker only exists across a few hundred metres of approach — which reads as a marker that never comes up. Meridian's six waypoints are ranged as a set for the same reason and not each on its own merits: the town's name carries the default outer edge and its five districts stop at 2800 m, because giving them all the same reach means arriving to six labels in one stack naming quarters that are still a single grey patch.

**Nothing is drawn through the globe**, and it takes two tests. The cheap one is exact and costs a dot product: the eye is above a landmark's horizon exactly when it is on the outward side of the tangent plane there, which is `landmark.global_basis.y` because `SurfaceAnchor` puts the radial in its own `y`. The other is `Planet.sight_blocked()`, which walks the height field along the sight line — a raycast cannot answer this, because only `collision_range` metres around the viewer have a body and everything worth naming is well past that. It is a dozen noise lookups, so the layer caches it for a quarter of a second per landmark and staggers the first check.

`dev/_city_test.tscn -- --hud` is the harness. It prints **which names were actually drawn** at each vantage, which is the whole behaviour and is far easier to read than a screenshot: the `waypoint_aimed`/`waypoint_aside` pair is the same place at the same distance looked at and looked past, and `waypoint_orbit` — the view the game opens on — naming nothing at all is the outer edge working. It then flies a ladder of altitudes down onto the Landing and reads the layer twice at each rung, aimed and aside, which is the check that names arrive partway down instead of all at once from orbit.

Two things about posing a camera for that harness cost time to rediscover. The vantages stand out to one side as well as up, so a row is **1.28 of its altitude away** from the place, and the ranges are read against the distance; write an altitude equal to a range and the marker lands exactly on its own fade edge. And a view swung about the local up is only taken off the crosshair while the camera is oblique — from directly overhead that axis lies along the view and the swing is a roll, so the place stays dead centre and every reading is the aimed one. `_pose` picks the axis from the angle for that reason.

### Saying where you are

`game/player/coordinate_plate.gd` is the top-right readout, raised on the local player's HUD the way `WaypointLayer` is and toggled with `F3`. It exists for one job: **letting somebody who is not here go and look at what you are looking at.**

That job is what decides its contents. A world position is useless for it — the origin is the planet's *centre*, so a spot on the grass is three five-figure numbers with no meaning outside the program, and nobody transcribes those correctly. So it reports latitude and longitude in the planet's local frame, which is two numbers with a hemisphere letter each, plus the height above sea level, the nearest named place, and the unit direction for anything that wants to be handed a vector. Longitude runs from local `+Z` counting east toward `+X`; that is a choice rather than a convention, and it only has to agree with the one place that reads it back.

**The other half is `dev/_planet_test.tscn -- --at=`**, which takes the string the plate prints — letters and all, `--at="34.21 S,118.55 W"` — and shoots that spot from 2 km, 300 m, 60 m and standing. A readout with nothing that consumes it is a decoration, and a coordinate that has to be converted from `S` to a minus sign by hand before it can be used is the step that gets it wrong. The two ends are inverses of each other and were checked as such.

The last line is a diagnostic rather than a location: the LOD depth the ground under you is drawn at against `max_depth`, how many chunks nearby have a collider, and — only while it is happening — how many drawn chunks are still waiting for one. That is what separates "the terrain is wrong here" from "the terrain has not finished loading here", which is a distinction no screenshot carries and the one most often needed before a report can be acted on. It is throttled to 6 Hz, because `Planet.statistics()` walks every drawn chunk and because a number that changes every frame cannot be read, let alone written down.

## 3. Character, animation and Blender assets

Assets are authored **as code**. `blender_assets/source/*.py` builds them, `blender_assets/*.glb` is the output, and the `.blend` files are intermediates. Run with the Blender version that last saved the `.blend` — opening a newer file in an older Blender drops data silently, and the reverse is safe, which is why the settler's last rebuild through 5.2 over sculpts written by an older Blender went through untouched. Scripts document Blender 5.1 (`build_character.py`'s header still says 4.5); 5.2 is what is installed.

**Every body and every garment the settler owns is authored white**, and that is a requirement of how they are coloured rather than a look. A tint multiplies the albedo it lands on, so whatever a `.py` bakes in is a *ceiling* on what the character editor can reach: the boots shipped at 0.17 grey and the tunic at 0.34, which meant nine of the colour strip's ten swatches arrived as the same near-black and the strip read as broken rather than as dark. `build_character_3.WHITE` is the one constant now, `SKIN_COLOUR` is it, and the `sculpt_colours` / `level_colour` / `GARMENT_LEVEL` machinery that used to read a hue per region off the dressed sculpt is gone — its whole job was to make three garments differ from each other, which is the player's decision. The cost is that an untinted figure is a blank, which is the right way round.

The astronaut's five garments in `build_apparel.py` are **still authored in colour**, deliberately: that body is `playable: false`, so nothing offers it or its wardrobe, and whitening them means a `build_apparel.py` run plus a `build_animations.py` rebake for a body no menu lists. Turning the astronaut back on means doing that first, or its clothes will not take a colour.

### The rig

23 bones, names matching Godot's humanoid profile, so a future agent can swap in a different character and keep the code:

```
Root → Hips → Spine → Chest → UpperChest → Neck → Head
                                        → {Left,Right}Shoulder → UpperArm → LowerArm → Hand
            → {Left,Right}UpperLeg → LowerLeg → Foot → Toes
```

1.45 m tall, feet on the floor, faces **+Y in Blender** which exports as **-Z in Godot**. Proportions live in the `TORSO`, `ARM`, `LEG`, `BOOT` tables and bone rests in `BONES` / `ARM_BONES` / `LEG_BONES`, all in `build_character.py`. `character_ref.py` measures the exported character (height, hand fit, back surface, arm drop) so weapons, backpack and workbench are sized **from the real mesh** rather than from duplicated constants — which also means re-exporting the character after changing proportions and rebuilding the props that depend on it.

If you change the character's height, three things in Godot follow: `COLLIDER_HEIGHTS` and `EYE_HEIGHTS` in `player.gd`, and the capsule plus `CeilingCheck` in `player.tscn`.

### Animation

Thirteen clips at 30 fps, authored as pose functions of cycle phase `t` and baked to NLA tracks by `build_animations.py`:

| Clip | Frames | Loops |
| --- | --- | --- |
| `Idle` | 90 | yes |
| `Walk` | 30 | yes |
| `Run` | 20 | yes |
| `CrouchIdle` | 72 | yes |
| `CrouchWalk` | 36 | yes |
| `JumpRise` | 11 | no |
| `Fall` | 36 | yes |
| `Land` | 13 | no |
| `Slide` | 12 | no |
| `Float` | 60 | yes |
| `Fly` | 48 | yes |
| `Tread` | 72 | yes |
| `Swim` | 36 | yes |

**Two pairs are authored upright and leaned by the game**, `Float`/`Fly` and `Tread`/`Swim`, because it pitches the body over as speed builds: in those four "up" is the direction of travel, and `Swim` is a front crawl written vertically, which is why its arms sweep the whole way round the shoulder rather than reaching forward. Author either flat-out clip lying down instead and it fights the rig's rest pose and leaves nothing usable at the hovering or treading end of the same continuum.

**Four of them are held at speed and all four sweep the arms back**: `Run`, `JumpRise`, `Fall` and `Fly`. Arms carried forward is what each of them did first and it is what a body really does — the arm swing is where a third of a jump's height comes from — but at the top of the swing the palms are up, the elbows are bent, and every one of them read as somebody feeling along a dark corridor. Arms back with the chest driven forward is the posture, and the legs then carry the difference between them: a stride, a split tuck, a trail, and a straight line.

**A clip that plays straight into another one has to agree with it at the join**, and `JumpRise` into `Fall` is the case to remember: a jump reaches its apex in about a third of a second and `_update_animation` switches on vertical speed, so that seam happens in the air in front of the player on every single jump. `Fall`'s arms used to swing forward into a bent-elbow hang while the leap had them swept back, and the character spent the top of every jump reaching out in front of itself — both clips looked right on their own, which is exactly why nothing caught it. `_check_character.gd` now measures the seams in `SEAMS` and fails past `SEAM_TOLERANCE`, taking the hand's position **in the chest's frame**: a torso settling out of the leap's arch moves a hand 15 cm on its own and should, and measured from the hips that drowns out the arm reversal being looked for.

Three helpers carry the authoring, and each exists because of a mistake worth not repeating:

- `rot(("Y", angle), ("X", angle))` — rotations apply **in the order listed**. Arms must drop before they swing; the other order twists the limb instead. Positive `X` swings a limb **forward** and tips a torso bone **back**, which is one rotation read at two ends of a bone and not a typo; see the file header, and measure a lean rather than eyeballing it.
- `leg_fold(drop, ankle_forward)` — two-link IK that keeps soles on the floor. Poses re-solve it per frame from the hip drop rather than scaling a precomputed angle, which is what stops feet sinking through the ground in crouch, land and slide.
- `arm_hang(pose, side, sign, out, swing, flex)` — poses state the angle the **finished** arm should read as, and this converts it to bone rotations. The rest pose is a wide A-pose (`ARM_REST_OUT` 41.8°, `FOREARM_REST_OUT` 47.8°), and the forearm inherits the shoulder's tuck, so hand-written pairs adduct it twice and the hands end up crossed over the hips. Re-measure those constants with `blender_assets/source/_arm_check.py` if the rig's rest angles change; it also reports arm-to-body clearance per clip, which is how "close to the hips" was kept from becoming "inside the hips".

Two export gotchas cost hours if rediscovered:

- **`export_animation_mode="NLA_TRACKS"` is required.** The exporter's default "Actions" mode silently writes **zero** clips for the slotted actions Blender 4.4+ produces, and the symptom is a null `AnimationPlayer` in Godot. Never export the character through Blender's own File → Export dialog.
- **Unhide, then select, in two passes.** Writing `hide_viewport` resyncs the view layer and clears the selection made so far, so interleaving the two exports only the last object. `export_glb.py` does it correctly and hard-fails if the selection came up short.

On the Godot side, `player_character.glb.import` keeps `animation/remove_immutable_tracks=false`; without it Godot strips tracks and poses bleed between clips.

### The second body: the settler

`blender_assets/source/build_character_3.py` builds the whole of the settler out of two MeshMaker sculpts that were never made for this project: `generated/character_3.blend` is a T-posed body with no usable rig, and `generated/dressed.blend` is a *different*, taller sculpt of a clothed figure. One run measures the body, builds a 45-bone rig with fingers into it, makes four garments, bakes the thirteen clips against its own proportions and writes `player_character_3.glb` plus four `apparel_c3_*.glb`. The astronaut's `build_character.py` is untouched by any of it; the two bodies meet only in the bone names and in `build_animations.py`.

**Both sculpts arrive facing -Y, and everything else in the project faces +Y.** `load_body` and `load_dressed` both call `turn_to_face_forward`, which measures the feet — the one part of a body decisively longer in front than behind — and turns whatever it finds. Neither trusts the file, because a body left facing backwards **does not fail anywhere**: every landmark this script looks for is symmetric in y except the feet, so it builds a rig whose toe bones are in the heels, passes `_check_character`'s toes-in-front test on those bones, exports a body that walks its clips backwards, and identifies the thumb as the little finger. The only symptom is a character who moonwalks. It also silently flips the dressed sculpt relative to the body, which puts the coat's front on the settler's back.

**Two of the three garments are grown off this body and only one is cut out of the sculpt**, and which is which is decided by whether the garment has to follow a body:

- The **tunic and boots** are `build_apparel.carve_shell` shells — the astronaut's own garment code, imported and handed specs written against `build_apparel.Landmarks` read off the settler's rig. A shell is a copy of the body's own faces pushed out along their normals, so it fits by construction, arrives carrying the body's skin weights, and cannot poke through. The boots come out as two separate shells because the body's feet are separate, and the build **prints the gap between them** (45 mm) rather than leaving it to a render.
- The **hair** is still cut out of the dressed sculpt and box-fitted onto the skull, because it is an accessory hanging off a head rather than cloth following a body, and no offset of a scalp would ever produce it.

Three things about that split are worth keeping:

- **A garment cut from one sculpt and box-scaled onto another does not fit, and cannot be made to.** That is what this file used to do for all three, and the tunic came out as bare shoulders with two shredded straps.
- **A per-vertex clearance pass turns cloth into confetti.** Snapping each buried vertex onto the skin leaves its neighbours a millimetre away exactly where they were, so a garment lying close to the body comes out as a fringe of alternating spikes and holes over its whole surface — not a poke-through here and there. `push_out` now **smooths the correction across the mesh before applying it**, so the cloth lifts as a bulge, and runs the pass a few times over because smoothing takes the peak off as well as the edges.
- **A body shell cannot make a skirt.** Below the crotch the shell splits with the legs, so a tunic taken any lower becomes a pair of shorts. The hem stops at the hip and is flared outward *from the vertical axis* instead — pushing along the surface normal there points inward between the legs — which is the difference between a tunic and a leotard.

Garment colours used to be read off the sculpt, averaged per region so the three did not come out as one muddy near-black. They are all `WHITE` now and the reading is gone — see the head of this section for why a baked-in colour is a ceiling rather than a starting point. The sculpt's own vertex colours never reached the `.glb` anyway; the exporter drops them because no material's node tree uses them, and albedo comes from the Principled BSDF's Base Color.

`bake_locomotion` hands `build_animations.py` this body's own measurements — leg root, ankle, thigh, shin, rest arm angles, plus `BODY_SCALE` and `STRIDE_SCALE`. The settler is 1.60 m and 47% leg against the astronaut's 1.45 m and 36%, and rests in a true T rather than a wide A, so nothing carries across as a constant.

### Attachment conventions

Each asset is authored in a local space that some Godot code assumes. Break the convention and the asset ends up inside the character.

| Asset | Blender authoring space | Consumed by |
| --- | --- | --- |
| `sword.glb`, `laser_rifle.glb` | origin at grip centre, aim along +Y, up +Z (Godot: aim **-Z**, up +Y) | `game/player/weapons.gd`, `weapon_pose.gd` |
| `apparel_*.glb` | body mesh derivative, shares the 23 joints, no animation | `game/player/wardrobe.gd` |
| `player_character_3.glb`, `apparel_c3_*.glb` | the settler and its four garments, 45 joints, **facing +Y** like everything else once `build_character_3.py` has turned it | `game/player/character_db.gd`, `wardrobe.gd` |
| `wardrobe.glb` | base at floor, doors face +Y, hinges on the outer edges | *nothing — the station it belonged to went when the menu took its job* |
| `backpack.glb` | origin at the `UpperChest` bone, +Y forward | *nothing yet* |
| `workbench.glb` | top at measured arm height, work face +Y, vice opens +Y | *nothing yet* |
| `cave_room.glb` | floor centre origin, tunnel along +X | *nothing yet* |

Apparel must **not** be exported into the body `.glb` — `export_glb.py` skips the `Apparel` collection, because welding garments into the body would take the wardrobe's job away. And `build_character.py` **overwrites the whole `.blend`**, animations included; use `export_glb.py` for a hand-edited file.

Verify assets headlessly: `_check_character` (bones, facing, bounds) and `_check_apparel` (garments share the skeleton and move with `Walk`) both run over **every body** and take `-- --body=settler` for one; `_check_weapons` (lengths, grip inside the fist, both hands), `_check_wardrobe` (door hinges), `_inspect_glb` (dump everything). Neither `_check_*` script may import `CharacterDB`, because `--script` runs without autoloads and `CharacterDB` reaches `SettingsManager` for the saved look — the paths are repeated in each. Previews render to `blender_assets/source/previews/` via the `render_*.py` scripts.

To look at a body rather than measure it, four Blender harnesses write to `dev/captures/`: `dev/_render_mesh.py` takes any `.blend` and shoots the biggest mesh in it **and prints which way it faces**; `dev/_render_dressed.py` takes a rigged `.blend` and shoots the body wearing everything in it, front, back, side and hero, with `--clip=Walk@8` to pose it on one frame of one baked clip, `--at=1.06` to frame a band of it and `--hide=hat,character` to drop objects by name — a garment fault is at a joint under a pose, and the three together are how you get the collar of a shirt on its own, mid-stride, at a size you can judge; `dev/_rig_report.py` dumps every bone's head, tail and length beside a true rest-pose render; and `dev/_render_rig.py` walks the character with cylinder proxies on the bones. Both renderers put the front shot at **+Y**; calling the -Y shot "front" is how a body that arrived facing backwards went unnoticed. They also have to mute the NLA tracks *and* reset every pose bone by hand, because muting alone leaves the bones holding whatever the last evaluated clip put in them and renders a "rest pose" with one arm in the air.

## 4. Co-op: menus, session, chat and voice

### Session shape

There is **no lobby scene, and no menu scene either**. `game/world.tscn` is the main scene, and it comes up empty: `world.gd` sees `NetworkManager.state == IDLE`, spawns nobody, and hangs the home screen over it. `start_single_player()`, `host_game()` and a successful join all just say a session exists, and the world spawns into itself. So the title, the lobby and the game are one scene from boot to quit, and the only scene change left is leaving a game, which reloads the world back into its empty state.

That is not tidiness, it is the only way New Game can be seamless: the planet's quadtree takes seconds to build, so a scene change anywhere between the title and playing is a stall the player watches. Anything that should exist for a whole session therefore belongs in an autoload rather than in the world scene — that is why chat and voice are autoloads, and why they would appear on a lobby screen for free if one were added.

The host owns everything that could be lied about: the roster (`players`, keyed by peer id), spawning, movement validation (speed clamps and a `MAX_ACCEPTED_STEP` teleport reject), the private lobby code, and the name attached to every chat line. Clients own their own **look** — equipment and held weapon are broadcast by the player who changed them, and a late joiner is told the lot in the world-state snapshot. `NetworkManager.in_multiplayer_session()` is the one test for "a session with other people in it"; single player reaches `IN_GAME` too.

### The home screen

`ui/menu/home_screen.gd` is a `Node3D` under the world, not a `Control` in front of it. It owns a camera, a preview character hovering at the spawn, and a `CanvasLayer` of text. Its three views are three **camera poses over the same scene**, tweened between: HOME frames the character left and the planet right, ONLINE pitches up so the planet's limb runs under the create and join forms, SETTINGS turns away into empty sky. `POSE_OFFSETS` / `POSE_YAWS` / `POSE_PITCHES` / `POSE_FOVS` are indexed by `View` and their row order must match the enum; the header there explains why the field of view is 90 and not 60, which is the one number that looks arbitrary and is not.

**Pitch and camera height do two different jobs on the HOME shot, and conflating them cost the whole composition once.** The planet is nine kilometres away and the figure is two metres, so the camera's *position* moves only the figure and its *pitch* moves both: pitch is therefore the one dial that decides where the planet sits and how much dark sky is left under it for the menu, and height is the one that decides where in the frame the figure lands. Raised to sit level with a 25-degree pitch, the camera looked 25 degrees down on a body whose middle is at 0.9 m and the home screen showed the top of its head.

That same split is what got the figure in close without losing it off the top. **Coming in makes the figure bigger about wherever it already is**, so the useful question is what to pull in *towards*: shortening all three components of the offset shrinks the distance to the figure's **feet**, which holds the feet still and grows the body upward out of them, and the head leaves the frame while the shins are still halfway down it. Pulling in towards the figure's own middle instead lets it grow both ways about a point that was composed on purpose, and that is the difference between 1.5x fitting and 1.2x not. Rising then drops the whole figure down the frame and leaves the planet exactly where it was. Reaching for the pitch to do that last part is the mistake — it would bring the planet down too and close the band the menu runs along. The figure now fills three fifths of the frame, head about a sixth down and feet three quarters, which leaves the name plate and the menu row the bottom quarter.

**The menu is a row along the foot of the window, not a list down the right.** The list was there because the figure owned the left and the planet the right, leaving one column of dark sky to put it in; the figure has since been brought in close enough to want the middle as well, and a row along the bottom crosses neither. **New Game does not start a game** — it asks which one, and the answer replaces the row it was pressed on rather than opening a screen, because two buttons are not a form and a card holding them would dim the very figure the modes differ about. `MODES` is the list; both entries call `start_new_game`, which is already the one place the world is handed the spawn and the look and is where a mode would go beside them.

**The figure also stands `PREVIEW_TURN` off dead-on.** `Float` draws one knee up and across the other and that silhouette is the whole of what says hovering rather than standing at attention — but it is drawn up *forward*, so a camera square to the chest foreshortens it away to nothing. Facing the camera exactly is what made the pose invisible; a third of a turn off shows the face and opens the knee.

New Game is the part worth understanding before changing it:

1. The home screen tells the world to spawn the local player at the **preview character's exact transform** (`GameWorld.override_local_spawn`), so the real body appears in the preview's shoes and the swap is invisible.
2. The player spawns with `defer_camera` set, so it does **not** take the viewport, the mouse or the HUD on the way in — otherwise it would snap the view on the frame it spawns.
3. The camera sweeps from the home pose to the player's own third-person camera while the body turns from facing the camera to facing the planet. On the home screen the character is turned to look at you, so "behind them" is empty sky; the turn is what leaves the player pointed at the world they are about to fly to.
4. `OnlinePlayer.take_camera()` hands over the viewport, mouse, HUD and controls at the end.

The forms are ordinary pencil-on-paper cards, because they need to be read: `ui/menu/settings_panel.gd` (Graphics / Audio / Gameplay, with the **controls list generated from `InputMap`**, so a new action is rebindable with no menu edit) and `ui/menu/lobby_panel.gd` (create and join side by side, which is all "Online" ever was). Shared rows live in `ui/menu/menu_widgets.gd`. A new setting needs an entry in `SettingsManager.DEFAULTS`, a control in the matching tab, and somewhere to be applied — which is a case in `_apply_setting` only when the thing it changes exists for the whole session. The manager runs from the title screen, so anything living in the world cannot be reached from there: `graphics/render_distance` is instead read by `Planet._follow_render_distance()` when a map loads, which also connects `settings_changed` so the level lands while the pause menu is still open. That matters for a visual setting more than for most — you pick a render distance by looking at what it did.

Bare text over the starfield is the one place the project's own legibility rule is turned around. Elsewhere a HUD line sits on an opaque plate and a button's label keeps its colour in every state; here a panel in the middle of space would read as a menu bolted over the game, so the type is Vanilla Custard with a near-black outline and Sunflower Gold still means "the thing you are on".

The title row is the title and BACK **side by side**, not stacked. Every card below fills the band under it, so a second line up here is a line taken off every screen — and the line that goes missing is whichever button the form ends with.

### Chat

`Enter` opens the line, `Enter` sends, `Escape` throws it away. `core/chat_manager.gd` holds the wire and the scrollback; `ui/chat/chat_hud.gd` is the panel. A client offers its line to the host, which paces it (`MIN_INTERVAL`), runs it through `core/text_moderation.gd`, then stamps it with the roster name and broadcasts. A blocked line is refused to its sender alone; a joining peer is handed the tail of the log, minus anything marked `local` (a peer's own notices are its own business).

Two behaviours are easy to break:

- **Escape must belong to the field while it is open.** The panel handles it in `_input`, which runs before every `_unhandled_input`, so the world's pause handler never sees it. Without that, abandoning a message pauses the game.
- **Typing must disable the player, not just focus a field.** Movement is polled, so a focused `LineEdit` does not stop `W`. The panel sets `controls_enabled = false` and restores it to **what it was**, not to `true`, because chat can be opened over a menu that was already holding the controls.

The same ownership rule cuts the other way now that `Escape` opens the menu: `GameMenu._input` **steps aside while `ChatHud.typing`**, since both handle the key in `_input` and the menu is deeper in the tree. `dev/_comms_test.tscn` is what catches it — the `paused` line reports whether the menu was still up after abandoning a message.

### Voice

Hold `V`. `core/voice_chat.gd` captures from the `Mic` bus, downmixes, resamples to 12 kHz, and sends one companded byte per sample as `unreliable_ordered` packets — about 12 KB/s per talker, with no codec to ship. A late packet is worth less than nothing, so a lost one is left as a gap. Each talker is played through an `AudioStreamGenerator` fed from a queue that holds back 100 ms; that prebuffer is the jitter absorber, and it re-arms when a talker goes quiet so the next word does not stutter in.

The audio wiring in `default_bus_layout.tres` has one non-obvious requirement: on the `Mic` bus the **capture effect comes first and an amplifier at -80 dB comes second**. Muting that bus or pulling its volume down — the obvious ways to keep the microphone out of the speakers — silences the capture tap along with the output, and the symptom is a capture buffer full of exact zeroes. The microphone also needs `[audio] driver/enable_input=true` in `project.godot`.

Voice is **not positional**: everyone is heard at the same level. Making it spatial means moving each talker's player onto an `AudioStreamPlayer3D` on that peer's body, and deciding what to do about a talker with no body yet.

## Recipes

**Add a garment.** Add a spec to `garment_specs()` in `build_apparel.py`; run `build_apparel.py` then `build_animations.py` (apparel does not export the body, and symmetrising changes the rest pose so clips must be rebaked); add the `.glb` path to `Wardrobe.APPAREL`; add an `ItemDB.ITEMS` entry with the matching `slot`; add the item id to that body's `apparel` list in `CharacterDB.BODIES`, or it will not be offered anywhere. Icons and tooltips need nothing further, and the Admin tab lists it for free. Verify with `_check_apparel.gd` and `dev/_menu_test.tscn`.

**Give both bodies the same garment** by writing the spec as a function of the landmarks — `goggles_spec()` is the pattern — and calling it from `shell_specs()` in `build_character_3.py` with the settler's own slug and colour. That is one build per body and two `ItemDB` entries, and the second body needs `build_character_3.py` re-run: it bakes and exports the settler's garments itself, so a spec added to `build_apparel.py` alone reaches the astronaut and nothing else.

**Add a playable body.** Add an entry to `CharacterDB.BODIES` with the `.glb`, the height, eye height and lean pivot measured off it, `playable: true`, and the item ids of the garments cut for its skeleton. Its garments appear in the editor's rail on their own. `playable` is the flag that separates a body the code still knows about from one a player may choose — the astronaut is `false`, which retires it from the menus without breaking anything that references it. Nothing else needs editing: the heights feed `OnlinePlayer._set_body`, and every garment the other body owns is refused on this one. Verify with `dev/_menu_shot.tscn`, which shoots each body dressed and prints what the spawned player ended up wearing.

**Add an equipment slot.** `ItemDB.SLOT_ORDER` (order is the UI order) and `SLOT_LABELS`, `Wardrobe.APPAREL`, and the garment `.glb`. The player's `equipment` container sizes itself from `SLOT_ORDER`.

**Add a weapon.** Author it in `build_weapons.py` on the grip/aim convention; add an `ItemDB.ITEMS` entry with `slot: "weapon"`, a `hold`, an `attack` and a `cell` if it needs ammo; add it to `Weapons.WEAPONS`; if it is held differently, add a `HOLDS` entry (plus `{hold}_aimed`) and a `PITCH_FOLLOW` value, then tune against `dev/_weapon_test.tscn`, which prints cant and hand separation. A new attack kind means a new `ItemDB.ATTACK_*` and an arm in `OnlinePlayer._attack`.

**Add a station.** A `StaticBody3D` with `interact(player)` and `interact_prompt()`, a collider, a model, and a screen built the way `ui/inventory/inventory_page.gd` is, wired to the player's containers. There is no station left to copy — the wardrobe's went when the menu took its job — but `OnlinePlayer.open_menu()` is still the seam a station hands its screen to. The workbench asset is already authored and waiting for exactly this.

**Add a town.** Find it first: `dev/_city_site.gd` sweeps the sphere for ground that is flat enough, sunlit enough and far enough from the towns already there, and prints the direction and the level to build at. Then a new layout file beside `meridian_layout.gd` — `KINDS`, `DISTRICTS`, `JUNCTIONS`, `ROADS`, `WAYPOINTS`, and a `plan()` filling a `CityPlan` — a `StringName` and two cases in `Settlements`, and a `CityBuilder` node under `Planet` in `game/world.tscn` naming the `site`. Nothing existing is edited. Verify with `dev/_city_test.tscn -- --site=NAME`, which needs a `VIEWS` and a `CROSS_SECTIONS` row for the new name: pick cross-sections **mid-segment on a road with no `bend`**, because a bend moves the carriageway off the chord between its junctions and a point computed from the two node positions lands in the grass.

**Add a road kind.** One row in that town's `KINDS`: `road`, `walk`, `kerb`, `lift`, `tone` and `deck`. `walk: 0.0` is a way with no footway and therefore no kerb, which is what a one-lane back street and a park path have in common. Everything downstream — the apron that makes it walkable, the junction setback, the tones at a crossing — falls out of `RoadProfile` from those six numbers. Check it with `--site=NAME`, which tables every kind against the player's step and slope limits before it measures the built collision.

**Add a quest or an achievement.** One row in `JournalDB.ENTRIES`: the `kind`, a `category`, the text, and a condition. Today the only condition is `landmark` plus `within`, naming the **node** in `game/world.tscn` rather than its title, so the title stays free to be reworded. A new category appears in the filter on its own. A condition nothing knows how to check is left permanently incomplete rather than treated as done, so a half-written entry is visible instead of silently rewarding itself.

**Add a stat.** One row in `PlayerStats.STATS` — title, description, base, range, unit, decimals — and it appears in the Inventory tab's list and in the Admin tab's picker. Making it *do* something is the separate half: `PlayerStats.value_of` is where a modifier would land, and `OnlinePlayer._on_stat_changed` is the pattern for a stat driving an export.

**Put it on the ground with a `SurfaceAnchor`** rather than by typing a transform. Parent the anchor to the `Planet` and the prop to the anchor; it works out the height from the same band-limited field the chunk meshes are built from, points local up radially, and turns the prop by `facing` about *that* up. A prop whose origin is at its base — which is the convention the Blender assets follow — needs no offset of its own.

**It solves in the planet's frame and writes in its parent's**, which only matters when the parent is not the planet. Hung under something that is itself standing on the ground — `CityBuilder` moves to its own town, and raises its waypoints as its children — the radius would otherwise be added twice and the anchor would end up 8 km up. Meridian's six waypoints were exactly that, at a radius of 16268 m, and it went unnoticed because a marker in orbit over a town still draws over the town from most angles: the shot looks like a town seen from further away than the harness asked for, which is not a thing anyone checks.

**In the editor an anchor is dragged, not typed.** It is a `@tool`, so moving it with the translate gizmo drops it back onto the ground under wherever it was let go, and turning it with the rotate gizmo keeps that heading while it stays flat to the surface — both by rewriting `direction` and `facing` from the transform the gizmo left behind. Duplicate a placed anchor and drag the copy: that is how a row of houses or a street gets laid out, and it is why a town does not need one hand-typed vector per building. `direction` is still there for a spot chosen by measurement rather than by eye, which is what `dev/_landing_site.tscn` prints — it searches the height field for the flattest dry ground on the **sunlit** face. Sunlit is not a nicety: one directional light lights the whole planet, so a prop on the night side renders flat and shadowless off ambient alone. That script hardcodes the sun direction to match the `Sun` in `world.tscn`, so re-aiming one means re-aiming the other.

**Each building wants its own anchor.** Parenting a whole street to one anchor puts everything but the centre on a tangent plane rather than on the ground, and the sphere falls away from that plane by about `d² / (2r)` — 0.6 m over a 200 m town, which reads as houses sinking at the far end.

**Add a road.** Put its ends in that town's `JUNCTIONS` as `Vector3(x, y, height above the pad)` — metres in the city frame — and add a row to `ROADS` naming the chain of junctions it runs through, a `kind` from `KINDS`, an optional `bend` per leg for a curve and `loop: true` to close it. **Reuse an existing junction id wherever the new road meets an old one**: sharing the id is what makes the two meet exactly, and it is what the audit checks. Nothing else needs editing — `CityBuilder` rebuilds the town from the graph and `RoadNetwork.audit()` prints the junction count, the reachable count and the dead ends. A road that names a junction nobody else does, one only reachable through itself, or one laid across another with no junction between them, is a hard failure there rather than something to be spotted in a screenshot.

**Add a district.** A row in that town's `DISTRICTS`: a `disc` or a rounded `box`, a position and size in the same frame, an optional `turn`, and a colour. Take the colour from `CityPlan`'s palette rather than inventing one — two towns each mixing their own grey for concrete is how a planet stops looking like one place. Later rows win where they overlap, which is how the park bites into the belt around it without either being a polygon. The zoning is a baked raster, so a district costs nothing per vertex however many there are; only `_bake_zones` walks them, once.

**Move a town.** `CENTRE` is a unit direction from the planet's centre and `FACING` the degrees that turn the town's `-y` to whatever it should face; both are `CityPlan` exports, so a harness can stand a town somewhere else without touching its layout. A town whose waypoints are in `world.tscn` — the Landing's are — has to have those moved with it; one that raises its own from `WAYPOINTS` follows for free, which is the better arrangement and what Meridian does.

**Add an input action.** `project.godot` `[input]`. It becomes rebindable in Settings automatically. Poll it (`Input.is_action_pressed`) for held state, read it from `_unhandled_input` for edges, and remember that only `Input.parse_input_event` reaches `_unhandled_input` in tests. If the key is one the GUI already claims — `Tab` is `ui_focus_next`, `Enter` is `ui_accept` — anything on screen has to catch it in `_input`, which runs first, or the focus system eats it.

**Reskin the whole game.** The 3D half is mostly data: the `region_*` globals in `project.godot` aim the colour wheel, `PlanetShape`'s biome constants set what the ground is under it, `planet_surface.tres` and `player_suit.tres` tune the ground and the character, and the `WorldEnvironment` in `game/world.tscn` sets the exposure everything is judged against. The 2D half is `ui/themes/ui_palette.gd` **and** the matching raw floats in `main_theme.tres` (which also owns the tab, popup, slider and scrollbar fills), plus the font import if you leave Barrio behind. The shaders themselves rarely need editing.

**Move the colour regions.** `region_turns` (whole numbers only) for how many there are, `region_phase` to rotate which hue lands where, `region_axis` for the pole they run around, `region_warp` for how much their boundaries wander, `region_chroma` for how strong the whole effect is. All in `project.godot` `[shader_globals]`, all read live by every vivid shader, so a change shows everywhere at once. Drifting `region_phase` at runtime slides the regions over the ground.

## Gotchas, ranked by how much time they cost

1. **Blender exports.** `NLA_TRACKS` mode, two-pass unhide-then-select, `Apparel` skipped, `build_character.py` overwrites everything. A null `AnimationPlayer` in Godot is always one of these.
2. **A sculpt facing the wrong way is silent all the way to the screen.** Everything faces +Y in Blender and -Z in Godot; both MeshMaker sculpts arrive facing -Y. A body left as it came still builds, still rigs, still passes the toes-in-front check — because the toe bones were built from the same wrong assumption — and only reads as a character who moonwalks. Measure the feet and turn the object; never take the file's word for it. `dev/_render_mesh.py` prints the answer for any `.blend`.
3. **`--import` after adding a `class_name`**, or nothing can see the new type.
4. **`rotate_y` turns the body about the *parent's* up, not its own**, so on a sphere it tips the player over instead of turning them and the view stops responding to the mouse. Every rotation of a body that lives on the planet is `rotate_object_local`. It is silent: the number of degrees looks right in a log, and only the axis is wrong.
5. **A thread pool takes the work off the frame, not off the CPU.** Twelve concurrent chunk builds cost 35 ms a frame of main-thread time on 24 cores, and it reads as the LOD walk being mysteriously slow — about 28 µs to visit a node that does a subtraction. Suspect contention whenever a GDScript timing is an order of magnitude worse than the work in it can explain, and confirm it by lowering the concurrency rather than by optimising the code being measured.
6. **The Mic bus effect order** (capture before the -80 dB amplifier); muting kills capture.
7. **The environment is part of the vivid look** — sky as ambient, ACES at `tonemap_white` 2.0, glow threshold under 1.0 because the mobile buffer tops out near 2.0. Copy them into any new scene or nothing matches.
8. **Procedural detail must fade with distance**, in two stages on terrain. Noise has no mip chain, so anything left on at range is shimmer from the ground and speckle from orbit.
9. **The 3D editor's far plane is 4000 m and the planet is 8 km across.** From the origin — which is the planet's *centre*, and where the editor camera starts — the ground is 8 km away and clipped, so the scene looks empty even with the preview running. Raise Z-Far in the viewport's **View → Settings** to see the globe at all, or skip it and select an anchor and press **F**, which drops the camera at the surface where the default far plane is plenty. Working at surface level is the normal case; the globe view is for checking where a town sits.
10. **Never turn the body to radial up out in space.** Looking straight down at the planet leaves no tangent to keep a heading in, so the view whips 90° sideways and the spawn shot is lost. `_alignment_blend` gates it on the atmosphere; the symptom of removing the gate is a spawn facing empty sky.
11. **HUD margins carry +6 px of `BLEED`**, and the plate goes on the `PanelContainer`, not the wrapper.
12. **Palette edits are two files**, and a control must never take the same fill as the surface behind it — that is what "white on white" was.
13. **A menu card that sizes to its contents will be clipped at both ends** once the contents outgrow the window, because it is centred in the band. Fill the band and scroll inside it instead — and a *fixed* card that is still smaller than its contents' minimum will be grown by them anyway, which is what pushed the Inventory tab's colour strip off the bottom of the screen. Compact the page; a share of the window is not a limit.
14. **Enum-indexed tables** (`COLLIDER_HEIGHTS`, `EYE_HEIGHTS`, `ARM_LENGTHS`, `SHOULDER_OFFSETS`) must keep enum order, `Stance` now has six rows, and a new one goes on the end because the index is what goes on the wire.
15. **Polled vs event input**: `Input.action_press` never reaches `_unhandled_input`; `InputEventAction` never satisfies a poll-based check the same frame. Tests need the right one, and UI hover needs a real `InputEventMouseMotion` in **window** pixels. **`Tab` and `Escape` are contested on top of that**: `Tab` is `ui_focus_next`, so a screen full of tiles eats it unless the handler is in `_input`, and `Escape` in `_input` beats both `_unhandled_input` and a sibling higher in the tree — which is why `GameMenu` takes them there and stands down for an open chat line.
16. **Only `Planet` writes the shader globals**, and `region_turns` must be a whole number or the wheel seams on the far side.
17. **Detail scales are cycles per metre**, so nothing carries between a 1.45 m character and a hillside.
18. **`SurfaceSkin` copies albedo only** — colour and texture, never roughness or normals. The shader makes its own relief out of the albedo instead.
19. **Headless has no audio and no `AnimationPlayer` you can trust** — the `_check_*` scripts pose bones directly for this reason.
20. **`Float`/`Fly` and `Tread`/`Swim` are authored upright** and leaned by the game, and **take-off shares its key with the jump buffer on land and with the up-stroke in water** (see Flight and Swimming above). Both are silent when broken: the first only looks wrong in motion, the second only shows up as a jump that stops working or a swimmer who cannot reach the surface.
21. **A transparent surface that writes no depth cannot hide itself.** The sea is one disc bent onto the sphere, so without `depth_draw_always` the far half of it is drawn over the near half and the ocean extends past its own horizon as a flat notched band. Anything else laid over the whole planet will hit the same thing.
22. **Buoyancy and splash gravity are both written per place, not as constants.** Lift is a multiple of `_gravity()` so retuning the planet's pull does not sink every swimmer, and a `ParticleProcessMaterial`'s gravity is a world-space vector, so on a sphere each splash has to be told which way down is.
23. **Timed harness measurements must count physics frames.** `await get_tree().process_frame` runs at whatever the machine draws — here twice the physics rate — so a speed quoted against it comes out half what it is. The water harness reported a 3 m/s swim as 1.5 before this was noticed.
24. **`is_on_floor` under-reports on the planet**, because half the ground has no collider yet and the rest is a triangulation the feet spend most of a run a centimetre clear of. Use `_grounded()`. A body that thinks it is falling gets air control and no stair step, and the symptom is catching on bumps a walk should ride over.
25. **A `PhysicalBone3D` is not a `RigidBody3D`.** It has no `constant_force` and no `continuous_cd`, its damp modes are its own enum, and it must be given its `bone_name` *before* it is parented or it binds itself to bone -1. The ragdoll's gravity is therefore an impulse applied per frame — which it would have to be on a sphere anyway, since the space's gravity points down the global Y — and its continuous collision is set on the RID through `PhysicsServer3D`.
26. **Inside a shell, the incidence angle never reaches ninety degrees.** It bottoms out at `acos(r / R)` — from 300 m under the cloud deck that is 75°, never more — so a detail fade written against `abs(dot(up, view))` alone is dead code and the horizon keeps crawling however the thresholds are moved. Fade on the footprint, `range / abs(facing)`, which is what a pixel actually has to average. The same sum is what catches the limb from orbit, where the distance is unremarkable and the obliquity is everything.
27. **Fade a periodic pattern out of the colour, never out of the phase.** Scaling the phase by a factor falling from one to zero does not remove what the phase was drawing: the hue still reads off it, so every pixel on the way down sweeps through as many turns of the spectrum as the phase was worth. Because a fade like this depends only on view angle, those turns land along lines of constant view angle, and the sky fills with concentric rainbow rings centred on the zenith — strongest exactly where the fade was meant to be removing them. Mix between the plain colour and the patterned one instead.
28. **`fwidth` is unusable downstream of a loop or a `discard`.** Derivatives are undefined in non-uniform control flow, so a fade driven by one in a marched shader silently becomes no fade at all — it returns whatever the neighbouring pixel happened to be doing. Infer the footprint from the step length and the view angle instead.
29. **Never step a march by dividing the span into a whole number of steps.** The count can only change by one, so the step length jumps by a fraction of itself wherever it does, and hard stair-stepped bands appear along every line where the crossing is an exact multiple. Size the step first as a smooth quantity and let the count follow it.
30. **A point test is only a swept test while the point moves less than the thing it must not miss.** At `fly_speed` the body covers seventeen metres a tick, so any check written at the end of a move is blind to everything narrower than that, and the failure looks nothing like a near miss: it is silent, and the player is simply inside the world. Anything asked once per tick about where the body *is* — the ground guard today, and whatever gets asked about lava, trigger volumes or a town's walls tomorrow — has to be asked about the path instead. `_rewind_to_entry` is the pattern.
31. **A teleported player is still standing where it was.** Both halves of `_grounded()` survive a write to `global_position`: `_footed` is the guard's answer from the old spot and `is_on_floor` is the last `move_and_slide`'s, and both are read before the next move replaces them. A harness that drops a player into the sky and calls `start_flying()` gets a flight that ends on the following tick — which is how `_descent_test`'s fast dive spent a long time measuring a free fall in the standing stance and reporting it as a flight. Nothing in the game hits this, because taking off is refused while grounded.
32. **Adding a node before freeing the one with its name silently renames it.** Godot will not let two siblings share a name and resolves the clash in favour of whoever was there first, so swapping the player's `Character` by adding then freeing left every later `get_node("Character")` empty. Remove the old node first. The symptom is a page of null errors nowhere near the swap.
33. **A tint multiplies; it does not replace.** Anything that lets a colour be picked twice has to repaint from the authored albedo between picks, or the second pick gives the product of both. Two meshes sharing one material make the same mistake in one pass.
34. **The city pad must not be band-limited, and it is the one thing on the planet that is not.** Every other feature fades out at coarse spacing through `_resolves()` so it cannot alias, and applying that habit to the pad breaks it: the chunk under the player's feet would draw the flat while the player's ground guard — which samples at whatever spacing the ground underfoot was drawn at, see 63 — agreed, but the chunk fifty metres away would draw the hills the city replaced, and the two would meet in a wall. Detail may fade; the ground may not. The 260 m rim is wide enough to be resolvable at any spacing the planet ever uses, so nothing is being risked by ignoring spacing entirely.
35. **A `MeshInstance3D` whose triangles wind the wrong way is invisible, not inside-out.** Godot culls front faces clockwise, so a ribbon emitted counter-clockwise is simply not drawn, and a road that is missing looks exactly like a road that is buried in the terrain — which is where two hours went. `dev/_city_test.tscn -- --bare` hides the planet and lifts the city out from under it, which separates the two in one picture.
36. **A shader effect is only ever right at one size, and neither the character nor the sea is the size it was tuned for.** `vivid_surface`'s manufactured relief is measured in cycles per metre and was set for a wall, so on a 1.45 m body the macro field is torso-sized blotches and the bump is lumps crawling over a face — it reads as unfired clay, and `player_suit.tres` therefore turns all five relief terms off. The colour wheel has the mirror problem at the other end: `vivid_water`'s `region_tint` does not fade with distance the way the ripples do, so from orbit it was the only thing varying across the ocean and it varies in bands, striping half a planet of flat water. Land carries the wheel because terrain breaks the boundaries up; a flat sheet has nothing to break them with. Before reaching for an effect's intensity, check it is not simply being asked to work at a scale it was never measured at.
37. **In `build_animations.py`, positive `X` tips a torso bone backward.** It swings a limb forward — one rotation, read at the two ends of a bone: a hanging arm's tip is its hand and goes forward, a standing spine's tip is its neck and goes back. The file's header said "forward" for both for a long time, and a sprint authored on that read leans *away* from where it is going, which from the side is close enough to upright that it passes as "the lean is a bit weak". It cost a full bake cycle. Measure it: `atan2` of the neck's position minus the hips' in y and z, over a few frames. Expect the chord to come out about 0.58 of the sum of the angles authored, because the lower bones carry the ones above them.
38. **Two ribbons crossing do not make a junction, they make three faults.** Each road's raised footway ends up laid across the other's carriageway, the corners between them are never paved because neither ribbon turns, and a pad dropped in the middle at carriageway height z-fights the carriageway it was meant to complete. Cut both back and build the crossing from the rings they stopped on. The general rule, for whatever swept thing comes next: **where two surfaces meet, one has to stop**, and the stop has to reuse the other's vertices — a seam built from two independent calculations is only ever as good as they agree.
39. **Depth reconstructed from the buffer is a distance to a point, not a thickness.** The surf needs how deep the water is, and the obvious reading — the opaque surface's distance less the water fragment's — is the length of the slant path through it, which at a grazing angle is long even where the water is inches deep. That version lays a band of foam along the entire horizon. Turn the sample back into a world position and take its **radius from the planet's centre** instead: `planet_radius` less that is the true vertical depth, from any angle. On a sphere this is usually the move — a difference of radii is view-independent where anything measured along the eye ray is not.
40. **A plane cannot cut a clean hem out of a surface it is nearly parallel to.** The intersection is ill-defined there, so it wanders over the quad grid a face at a time and the opening comes out as a sawtooth — bisecting along the plane first does not help, because the ambiguity is in the geometry and not in the algorithm. The astronaut's collar spent a long time on the shelf where the shoulders run into the throat, which is the most up-facing band on the whole body, and looked torn in every pose while every attempt to fix it reached for thickness. Site a hem where the surface is *steep*, and measure that rather than eyeballing it: walk the mesh in 10 mm bands and average `abs(normal.z)`. The same goes for anything opening against a hip or the top of a foot.
41. **A shell garment cannot clip at rest, so measuring one at rest measures nothing.** It is the body offset along the body's own normals with the body's own weights; the two surfaces are parallel until something poses them. Every fit number worth having is taken over a few frames of the bendiest clips — and getting there means stepping over two traps that each return an answer wrong by a factor of ten. The depsgraph hands back whatever pose the `.blend` was saved in unless `pose_position` says otherwise; and the body's Decimate re-collapses differently for every pose, so a per-vertex mask taken in one pose indexes a different mesh in the next. Switching the Armature modifier off fixes the first by causing the second. Drop the Decimate instead.
42. **A screen-space effect nobody can measure needs an A/B, not a screenshot.** The surf is a depth read inside a fragment shader, so no number in GDScript can see it, and one picture of a coast cannot say which of the pale band along it is new foam and which is the shallow water that was always there — the first shot was misread twice. `_water_test` now shoots the same frame with `surf_strength` at 1 and at 0 and differences them, which turns "it looks about right" into 11.7% of the frame at a mean of +0.40. That is also what caught the foam saturating at grey: the coverage was fine and the peak would not rise, which pointed at the lighting term rather than at the shape. A **visibility** is muted by making it enormous, not by zeroing it: zero divides by it and leaves the effect at full.
43. **A raised road is a wall until something measures it against the player.** A two-foot roadbed is 0.61 m and the step is 0.30 m, so the whole town is enclosures unless every edge is ramped inside 45° — and the ramp has to carry the road's **fall**, which on a kerbed road is the footway and not the carriageway the lift is quoted to. Sizing it from the lift alone built 36.7° where the table printed 30, passable by luck. Two numbers that belong to another file (`step_height`, `floor_max_angle`) decide whether a whole district is reachable, so the harness prints both and walks out across a real road of every kind rather than trusting the arithmetic that produced it.
44. **A curve does not cross what its chord crosses.** Any test written on the straight lines between junctions is testing a road nobody built: `bend` bows the centreline off that chord by the bend itself, which on this layout is up to 24 m. The crossing audit reported nineteen faults on chords where ten existed on the real lines, and a sweep of false alarms is worse than no check, because the ten real ones were sitting in the middle of it. Audit the tessellated geometry, the same array the mesh is swept along.
45. **A hundred screenshots of a city will not show you a road laid through another one.** The Landing had ten, for as long as it has existed, and every one of them was photographed repeatedly without being seen: two ribbons at the same height read as a junction from above, and from the ground you are standing on one of them. It took a check that never looks at the picture. The general form: **a fault that renders is invisible to review**, and the only thing that finds it is a test written against the data the renderer was given.
46. **`look_at` takes a world point, and this world's origin is 8 km underground.** It is the planet's centre, so a review camera aimed at a bare `Vector3(0, 0.68, 0)` — which is what you write when the origin is the ground at the player's feet, and what every camera in `_player_test` did — points straight down into the core. The whole clip sheet came out as the inside of a hillside: forty screenshots, all of them plausible-looking files, none of them of the character. Aim through the subject's own frame (`_player.to_global(...)`) or set `rotation` locally. **The general form of this is worse than the specific one**: nothing about the flat-arena code failed when the arena became a planet, it just started measuring and photographing the wrong place, quietly.
47. **"Nothing is behind this" and "something is behind this at a negative depth" are different questions.** A depth read gives both, and folding them into one sign test is how the shoreline fade came to do the exact opposite of its job: dry land behind a water fragment reads as a *negative* water column, so `under < 0.0` meant "open sky past the limb" and also, silently, "the beach" — which was handed full opacity by the branch written to protect the limb. The fault looked nothing like a bad test, it looked like the fade not working, and two rounds of widening it made it worse. Carry the "is there anything there at all" answer as its own flag.
48. **Isolating a system by switching it off also switches off what it publishes.** `--nosea` skipped `PlanetWater` entirely, which took the murk globals the *terrain* reads away with it, so the one comparison the flag existed for — is this artefact the water or the bed? — changed both sides at once and cleared the water of a fault that was entirely its own. Hide the output, keep the object. Any A/B against a node that writes shader globals, publishes a frame or registers itself somewhere has this shape.
49. **A harness that poses a camera can quietly measure a different case than the one it names.** The waypoint ladder swung the view 40° off each landmark to read the ordinary range, and from directly overhead that swing was about the axis the view already lay along — a roll. The place stayed dead centre, so every rung read the *aimed* range instead, and the honest result of that (a name that comes up at 3400 m and goes again at 2400) reads exactly like a marker flickering on a bug. Half an hour went on the layer, which was correct throughout. When a measurement looks like a fault in the thing measured, **check that the harness set up the case in its own label** before reading the code under it.

50. **A veil has to be the last thing a fragment shader writes, and "multiply then assign" silently is not that.** `vivid_clouds` dims the deck by the water in front of it — colour, emission and alpha together, so a deck the sea should hide completely gives way to the sky's own version of it. The alpha line sat six lines above an `ALPHA = clamp(...)` that assigned the finished opacity outright, so the veil's colour multiply survived and its alpha multiply was thrown away. That is not a subtle tone error: it is full opacity carrying a colour scaled to nothing, which is **black**, and looking sideways a few metres down — where the chord out of the water is hundreds of metres and the transmittance is essentially zero — it was the entire sky. Anything that attenuates a finished fragment has to run after everything that writes one.
51. **A vantage has to be lit before a photograph of it is worth taking.** `_water_test` chose its swimming vantage as the deepest water on the planet, and one directional light means the deepest water is as likely to be at midnight as anywhere — it was. So the four shots that exist to show what the sea looks like from *inside* were black rectangles with stars in them, whatever the water was doing, and a cloud deck rendering solid black under water survived every one of them for as long as they had been running. `_landing_site.gd` already knew this and searches the sunlit face; the rule generalises to any harness that picks a spot on the globe by measuring the ground. The deepest-point statistic stays global; only the camera has to be somewhere the sun is.
52. **Idle workers and a backlog at the same time mean the work is being asked for too late, not that there is too much of it.** The chunk pool sat 61% busy with 43 chunks queued, which reads as saturation and is its opposite: capacity was going unused because dispatch ran only on the 30 Hz walk, so a slot that came free at the wrong moment waited 33 ms, and a queue-depth cap sized for the old expensive build was withholding splits while builders idled. Both fixes are the same shape — **let a throttle read the resource it is protecting** rather than a proxy for it, since the queue runs 80 deep when everything is healthy and no fixed mark on it means anything. Wherever a queue and a starved worker pool coexist, suspect the gate before the throughput.
53. **A budget spent by `sort_custom` can be dearer than one spent by rescanning the list per pick.** Sorting a few hundred split candidates once looks strictly better than 26 linear scans over them — thousands of comparisons against tens of thousands of array reads — and measured worse on both refine time (6.25 ms to 8.51) and chunks delivered (2856 to 2618), because each comparison is a script call and one of those outweighs the dozen inline reads it saves. GDScript's callback overhead moves the crossover a long way from where the complexity puts it.
54. **Throughput and latency are different questions, and optimising one can leave the other untouched.** Chunk delivery on the benchmark crossing nearly tripled while the time for a new place to sharpen did not move at all, because the crossing measures ground built *anywhere* and the complaint was about ground built *where the player is standing*. The metric that finally matched the complaint — depth of the drawn chunk underfoot — took ten minutes to add and immediately showed the ground running five levels coarse at speed. **Before optimising, write the measurement that would go green if the user were happy**; a number that improves threefold without the symptom changing was never measuring the symptom.
55. **When a cost is invariant to every budget you can turn, it is the work itself and not the schedule.** Converging four levels is 956 chunk builds, and it stayed 956 across pool width, upload budget, walk rate, split budget and lead distance — several of which are the obvious suspects and all of which did nothing. An invariant like that is the useful finding, not a dead end: it says the only remaining levers are the cost of the unit of work and how many units are needed, and it retires a whole shelf of tuning in one measurement.
56. **`_show` needs coverage, so growth spent nearest-first buys a spike that draws nothing.** The nearest child of the nearest chunk is nearest again, so a budget ordered purely by distance walks one chain down instead of filling an area; its siblings never arrive while the pool is busy, and a level with a hole in it cannot be drawn at all, so the ground underfoot falls all the way back to a whole ancestor — depth 2 out of 9, held indefinitely. It looks like a rendering fault and is a scheduling one. Anything with a "all N parts before any of it counts" rule downstream has to be fed breadth-first, whatever the priority order says.
57. **A queue that is only drained once a frame is a throughput cap wearing a concurrency cap's name.** `pending_limit` reads as "how many builds may run at once", and it is also "how many builds may *finish* per frame", because finished tasks are collected in `_apply_finished`. At 4 that is a hard 240 chunks a second at 60 fps whatever a build costs — so making builds ten times cheaper changed the arrival time by nothing at all, and the pool honestly reported itself 100% full the whole time while the workers were 95% idle. The tell is a delivery rate that comes out as an exact multiple of the frame rate. Ask what the ceiling is *before* optimising the thing under it.
58. **A GDScript call into a GDExtension resolves against `ClassDB` under a global lock unless the variable is typed.** Held as `Object`, every `_field.elevation(...)` took a read lock four worker threads were also taking a few thousand times a chunk; the port came out *slower* than the GDScript it replaced, and looked like the native code being mysteriously bad rather than like contention. Typing the variable to the extension class is the whole fix — 0.194 µs a bare call to 0.028 — and it applies to any hot call on an untyped `Object`, extension or not.
59. **Porting a function is worth what the function is, not what the language is.** Moving the height field to C++ was expected to be a tenfold win and delivered 2.6x, because 28 of its microseconds were `FastNoiseLite` — which was already C++, called from GDScript. The tenfold win was sitting one level up, in the *loop*: 90% of a chunk was the GDScript grid pass around the samples, not the samples. Measure the caller before rewriting the callee; a hot function inside a hotter loop is the loop's problem.
60. **A refactor that moves a branch also moves everything that used to come before it.** `color_at` returned water early, above the town loop, so sea was never zoned. Delegating the body to the native field left the loop behind and it now ran over every colour, painting the Landing's harbour with zoning concrete — 3 samples in 4096, invisible in any screenshot. When a function is split in two, the surviving half inherits every `return` the moved half used to shortcut.
61. **A transient-only fault is invisible to any check made after things settle.** Coarse chunks carried no collision soup, so for the whole of an arrival the ground you could see had nothing to stand on — 81 of 81 downward rays passed through it half a second after landing somewhere new, and 0 of 81 did once the tree had converged. Every check that existed asked the settled question and every one of them passed. The general shape: **a budget or a gate that resolves itself over a few seconds turns a permanent fault into a temporary one, and a temporary fault needs a measurement taken during the window, not after it.** Where a system has a warm-up, the harness has to sample inside it.
62. **Quantising a ridge does not make a mesa, it makes a jagged crown.** A bench is only as wide as the slope under it is gentle, so terracing applied over full mountain relief gives eighty-metre steps that read as crinkle. Flatten the ground to a broad uplift first, then quantise. The companion trap is periodicity: colour banding whose height divides the terrace height evenly puts every bench top in the world on the same course, and a hemisphere comes out one flat salmon — **two periodic fields stacked on the same axis must be incommensurate**, or the second is invisible everywhere the first is flat.
63. **Anything asking where the ground is on behalf of a *body* must ask at the spacing the ground was drawn at, not the finest.** Every feature in the height field fades out at coarse spacing so it cannot alias — that is gotcha 8 and it is correct — but the consequence is that a chunk which has not refined yet is missing whatever is finer than it, and a canyon is very nearly a step function, so what is missing is *the hole*. The coarse chunk draws a lid straight across it. `_catch_ground` sampled at `finest_spacing()` regardless of what was on screen, so under a lid it read the body as thirty-six metres in the air while it stood on ground it could see, handed it air control and no floor snapping, and let it sink through onto the canyon floor. `Planet.spacing_underfoot()` is the answer, and getting it right is a second job on its own — see `_note_underfoot`, where "the chunk underfoot" turned out to mean containment rather than nearness, twice. Note how this hid: settled, the drawn surface and the finest field agree to a few centimetres, so **every measurement taken after the tree converged said the guard was fine** — the same shape as 61, and the reason the readout now prints the collider and the field side by side is that their difference is the only thing that ever showed it.
64. **Whatever an asset is authored in is a ceiling on what a tint can reach, not a starting point.** A tint multiplies, so a boot baked at 0.17 grey can be tinted to any dark and to no bright at all: nine of the colour strip's ten swatches came out as the same near-black, and the read on that is "the colour picker is broken" rather than "the boot is dark", because the one thing a picker has to do is look different per swatch. The fix is in the `.py` and not in the UI — everything the player may recolour ships white, and the figure being a blank until they choose is the correct end state rather than a regression. Watch for the same shape wherever a multiply is the composition rule: the authored value stops being a look and becomes a limit.
65. **A card is never clipped by a host it does not fit — it drags the host past its own anchors.** So a screen laid out too wide is not missing an edge in the screenshot, it is a screenshot of a layout that has quietly moved, and what actually goes is whatever was last down the column. `dev/_menu_shot.tscn` prints `card wants WxH` against the room the anchors allow, which is the only reading that catches it. **And the room has to be computed from the anchors**, not from the parent's size: that check read the whole window while every screen was full-width, and the first screen held to a share of it passed with a card overflowing by 400 px.
66. **A handle is the only way to turn a thing off, so replacing a handle without freeing what it pointed at strands that thing on screen forever.** `_attach` assigned `chunk.instance` over the top of an existing mesh. `chunk.instance` is what `_set_visible` writes through and what `_drop` frees through, so the displaced node stayed parented to the planet, kept whatever visibility it was last given, and became unreachable by every line of code capable of hiding it. It cost **370 permanently drawn meshes** in fifteen seconds of standing still. The worst of them are orphaned *parents*: coarse, smoothed ground floating above the refined chunks that replaced it, never collidable — a collider belongs to a chunk and the chunk has moved on — which reads exactly as "extra terrain on top of the terrain, and you fall through it". It hid behind two things. The plate said `mesh` and `field` **agreed**, because both describe the live chunk and neither can see an orphan; and in `build_patch` the collision soup is sliced out of the same vertex array as the drawn triangles, so "drawn and solid are the same surface" was provably true of every chunk and still not true of the picture. **When the geometry checks out and the screenshot does not, count what is being drawn.** `_visible.size()` against the mesh children of the planet is what found it, and `statistics()["stranded"]` — incremented in `_attach` on the overwrite itself — is what keeps it found: `_perf_test` prints it on the `tree` line and zero is the only correct reading.
67. **A standing work queue needs the completion test, not just the in-flight test.** `_requests` deliberately outlives the walk that built it so the thread pool never idles, but `_apply_finished` runs every frame and clears `queued` the instant a build lands. Between that attach and the next walk, a chunk that was finished *and already drawn* still looked like an outstanding request, because `_dispatch` asked only whether it was in flight. So it was rebuilt, and rebuilt again — which is what fed 66 its orphans. Any queue whose entries are removed on a different clock from the one that adds them has to test for **done** as well as for **doing**.
68. **A probe cast for a body hits that body, unless it is named.** The coordinate plate's floor ray is `collision_mask = 1` with the comment "the player's own capsule is not the floor" — but the player is *on* layer 1, like the terrain, so a mask cannot separate them. Cast from 3 m up through a 1.45 m capsule standing at the origin, it hit the capsule's own crown and reported a floor 1.55 m **above** the feet, every frame, everywhere. The line that exists to say whether visible ground is solid therefore never once printed `NO COLLIDER`, and three separate attempts to find a terrain hole were made against an instrument that could not report one. Exclude by RID (`query.exclude`); a layer is a category and the thing you are asking on behalf of is an individual. The general form: **when the only instrument for a fault has never once fired, suspect the instrument before the fourth attempt at the fault.**
69. **Count the fault before you test whether you can fix it.** `_update_collision` folded "has collision faces" into the same `near` test that gated building a body, so a drawn chunk that somehow had no faces was skipped *and* left out of `_floorless` — the one hole that could never drain was the one hole the counter could not see, and it read zero precisely when the fault was permanent. Increment the diagnostic on the condition being diagnosed, then `continue` on whatever makes it unfixable this frame.
70. **A check that finds its subject by counting parents starts measuring something else the moment a container is inserted.** `_report_fit` reached the editor's card with `get_parent().get_parent()`, which was right until the editor grew a tab strip and a page host between the two — after which it measured the strip, and a strip fits whatever it is given, so the run went green on a card 43 px too tall. **The failure mode is the dangerous one**: not an error, not a wrong-looking number, but a pass. Walk up for the node by *type* (`_card_above` takes the outermost `PanelContainer`), and treat "the check still passes after a layout change" as something to verify rather than to be reassured by.

## Loose ends, deliberate and otherwise

- `blender_assets/backpack.glb`, `workbench.glb` and `cave_room.glb` are authored, verified and **not placed in any scene**. The in-game "backpack" is a 36-slot container, not that mesh.
- All 11 textures in `images/` are unused until assigned as Blender albedo (see §1).
- `game/player/player_accent.tres` is referenced by nothing since the character's materials were reworked; safe to delete.
- `fonts/PressStart2P-Regular.ttf` is the previous typeface, kept but no longer referenced. Its import settings are the pixel-face ones (antialiasing, hinting and subpixel positioning off), so putting it back means restoring the 8 px size grid as well.
- **Gravity is radial and the whole arc works** — orbit, descent, touchdown, walking — but only against `world.tscn`'s single planet, found by walking the player's siblings for a `Planet`. A second world body, or a planet that is not a sibling of the player, would need `_planet_below` to choose rather than to take the first one it finds.
- **The flat arena is gone**, and with it the six props and the kerb course, which is what `_player_test` was driving against.
- **There are no interactables left on the planet.** The wardrobe station was the only one, and it went when the menu made walking to a piece of furniture to change your hat pointless. `OnlinePlayer`'s reach cast, `interact()` seam and prompt plate are all still there and untested against anything; `blender_assets/wardrobe.glb` and `workbench.glb` are both authored and waiting.
- `shaders/pencil/` is retired in 3D and **live in 2D**: `pencil_ui.gdshader` draws every menu, HUD plate and pause card. Nothing in a scene points at `pencil_surface.gdshader` or `outline_passes.tres` any more, and `pencil_material.tres` is a preset for a shader nothing uses.
- `blender_assets/cute_astronaut_player.glb` is a legacy test asset used only by `dev/shader_lab.tscn`.
- The home screen's character floats rather than stands, because the spawn is in orbit and it has to match the body that replaces it. If the spawn ever moves to the ground, `Float` in `home_screen.gd` becomes `Idle`, `PREVIEW_TURN` goes back to zero — it is there to show a knee no standing pose draws up — and the camera pose wants re-measuring against `dev/_menu_shot.tscn`, which prints the clip and the hip height beside every home shot for exactly that reason.
- **Stats are listed, not yet spent.** `PlayerStats` keeps a base and an effective value apart so that a modifier has somewhere to live, but nothing modifies anything: speed drives the movement exports and health is a number on a bar that no damage reaches.
- **`_perf_test -- --arrive` still reports the collider 81.6 m off the field**, at lat 11.80 N lon 84.55 W, and it is the same 81.6 m settled as it is half a second in — so it is a place, not a timing window. It is **not** a missing collider: 0 of 81 rays come up empty at either moment. It is one spot where the triangles and the field disagree by more than any single feature is tall (`terrace_height` 32, `hoodoo_height` 17; a slot canyon is `canyon_depth` 120 but resolves at every spacing this probe uses). Worth its own session with a probe at that exact direction; it is stable, so it will keep.
- **`_descent_test` reports `collider 36%, grounded 69%`** on a 10 m/s sprint over settled ground. The first is expected and is the whole reason `_footed` exists; the second means a third of a jog is spent with air control, no floor snapping and no stair step, which is the budget "catching on bumps" comes out of. How much of that is a run genuinely leaving the ground has not been established.
- **Both character tabs have room going spare and it is now plain card.** Splitting the page in two doubled how much of it there is — Hero Design gave its pockets grid away and Inventory gave away everything but the grid. It was captioned "Reserved" wells for a while, on the reasoning that named room stops the next panel being wedged between two others; that was wrong on screen, because a well the size of half the card is the biggest control on it and reads as the thing you came for. Blank card says the same and does not compete.
- **Vacationer's Landing is streets and zoning, and nothing has been built on it yet.** The layout is drawn around the buildings that are meant to come — a downtown grid for towers, a park with no roads in it, a pedestrian Strand for bars, wharf spurs, cul-de-sacs — but every lot is empty ground. Placing anything on it means an anchor per building, per the recipe above; `CityPlan.surface_at()` gives the exact point on the pad for a spot on the city map.
- **Meridian Flats has no buildings and no station either**, and it is emptier than the Landing on purpose: it was laid out to exercise the road code — acute junctions, one-lane lanes, kerbless paths, a rotated grid — so its districts are zoning and waypoints only.
- **Each town is one static mesh built at `_ready()`.** There is no LOD and no culling beyond the one AABB per town, so all 50k of the Landing's triangles are submitted whenever any of it is in view, and now 19k of Meridian's alongside. The two are far enough apart that only one is ever near the camera, which is the only reason this is still free; splitting the draw per collision tile is the obvious first move when it stops being.
- Shared, contested storage does not exist: container **contents** are local, so two players at one wardrobe each see their own copy of the rail. Real shared storage needs a host-owned inventory.
- Chat and voice are session-scoped, and single player never sees them.
- Flying with a weapon in hand loses the flight pose's arms, because `WeaponPose` runs after the clip and the hold wins. The body still lies flat, so it reads as a flying figure carrying a rifle, which is why it has been left alone.
- **The native field is built for `target=editor` only.** That is the one an editor and a debug run load; exporting a release build needs `target=template_release` built as well, and `bin/planet.gdextension` already names the file it will look for.
- **Arriving somewhere new is 1.67 s to full detail, not instant**, and the pool is still 97% busy the whole time — so the remaining wait is supply, and raising `pending_limit` shortens it further at the price of churn while flying. Ground underfoot is at depth 6 of 9 within a third of a second, which is what stops it reading as terrain changing while you walk.
- Steam migration is planned but not started; the five steps are at the end of `README.md`. The topology stays player-hosted, so the work is confined to `NetworkManager`'s peer creation and `LanDiscovery`'s job of finding lobbies.
